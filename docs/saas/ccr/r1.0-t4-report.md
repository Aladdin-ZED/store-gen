## 3. The attack suite and the replay

### `scripts/qa/tenancy-check.ts` (`npm run test:tenancy`)

**Setup.**

- **Database.** It creates `cod_test_<script>` (or `--db cod_test_*`), migrates it, seeds it, and drops it at the end.
  Nothing is left behind.
- **Stores and people.** Two active stores, A (the victim) and B (the attacker), each with all six R1 roles. Besides
  them:
  - a member of both stores (viewer in A, owner in B);
  - a signed-in outsider;
  - a `super_admin` with no membership.
- **A's records carry canaries.** These are read back from the rows, so a seeding change cannot drop one silently.
  - Customer fields hold canaries in their masked part: last name, middle phone digits, address, note, e-mail.
  - The rest: pages, versions, labels, alt text, pixel labels and ids, tokens and test codes, the Turnstile secret,
    the store export key, the spreadsheet id, the legal name, the audit meta, the invite, the export.
  - Every id is a canary too.
- **Calls run in process.** Every call goes through the request-context seam (`runAsIdentity`, §E.4), inside Next's
  own work and request stores, so `revalidatePath`, `after()`, `headers()` and `cookies()` behave as under
  `next start`.
- **The network is fake.** `fetch` answers from a fake Google: an OAuth token, Sheets values and writes. Every request
  is recorded, and everything else (CAPI) is refused.

**The rule for every attempt:**

- it answers exactly what the same call with a missing id (or an unknown handle) answers;
- it returns no canary of A, not counting strings the caller sent itself;
- A's rows are byte-identical before and after. The fingerprint covers every tenant table, the store row, its members'
  users, its media chunks, its rate buckets and its usage counters.

### `scripts/qa/action-replay.ts` (`npm run qa:action-replay`)

The replay uses the same fixtures as the attack suite. For each of the 54 store actions it takes the body A's owner
sends and goes through these steps:

1. Replays the body as every attacker, to A's path and to B's path with A's ids, while A's records still exist.
2. Runs A's owner's own call with that body. It must work, which proves the replayed body was live.
3. Replays the body again after A's call.
4. Checks that A's rows are unchanged by every replay, and that no replay sent A's tokens over the network.

The Origin cases (CRIT2-11) come last: same origin works; `Origin: null`, no Origin and another site are refused with
`forbidden`, never a 500. They become real checks once T2's `storeAction` calls `assertSameOrigin`, which the script
detects in `seam.ts`. The run is in process; the HTTP transport (browser-recorded `Next-Action` ids) is the
integration's (CCR r1.0-t4-14).

## 4. Defects found by this step and fixed (T4 files)

1. **Impersonation leaked the typed phone number.**
   - **What:** `orders.phone_raw` passed through `maskCustomer` unmasked. Staff "viewing as" a store would have seen
     every customer's full number in the order list and the order detail.
   - **Fix:** `src/lib/admin-data/mask.ts` now masks it like the E.164 phone. The orders self-test has three new cases.
2. **An export allow-list could name the platform's own host (SEC-23).**
   - **What:** `normalizeAllowedOrigins` accepted `PLATFORM_HOST` (any scheme). A connected export could then take
     orders posted from every store's pages.
   - **Fix:** `src/lib/export/options.ts` refuses the following at save, with a field message:
     - `PLATFORM_HOST`, a legacy platform host and `ADMIN_HOST`;
     - the store root domain and its subdomains;
     - a wildcard that covers any of them.
   - `originAllowed` (T3) refuses them again at check time. The route returns 422 and no export row is written.
3. **The anti-spam form refused its own masked secret (a regression from step 4).**
   - **What:** `saveTurnstileAction` validated the secret's mask (`••••a1b2`) as a token, so the form could not be saved
     without typing the secret again.
   - **Fix:** the mask now reaches `updateStoreSetting`, which keeps the stored secret.
4. **Lint conformance in T4's files (no leak, but R1.0 exit criterion 1 needs it):**
   - **L9 (AUTH-31):** the 12 builder actions and `savePixelEntryAction` now open with `return storeAction(…)`. They
     use `reads` / `writes` body builders and an `entryKeys()` helper; behaviour is unchanged.
   - **L7:** the preview route and `components/admin/orders/parts.ts` no longer import `@/lib/db/*`.
   - **L8 and L13** were already clean in T4's files.

## 8. Deviations

1. **The replay runs in process, not over HTTP with Playwright** (as §F.1 describes `qa:action-replay`). This worktree
   may not run `next dev` / `next build`.
   - The replay calls the same exports a `Next-Action` id resolves to, with the replaying session's identity and path.
   - The HTTP transport and the Referrer-Policy / pre-hydration case are the integration's to add, on the same bodies
     (CCR r1.0-t4-14).
2. **The page payload is a server-side approximation of the RSC payload.** Server components (async and sync) are run
   up to the client boundaries, and the props of the client components are scanned. A canary rendered only inside a
   client component's own fetch would not show. The dashboard's client components fetch from the `/api/app` routes,
   which the routes suite attacks directly.
3. **The task names the roles "in store A against store B". The suite follows §F.1's naming:** A is the victim and B
   the attacker. The two are symmetric.
4. **T1's stubs are answered by an adapter inside the suites** (store settings as plain JSON, an HMAC and AES-GCM under
   a random test key, features on, in-memory counters, a plain store loop). Without it, most store paths would answer
   `server` and prove nothing. This follows the pattern of `pixels-publish-check.ts` and the media self-test.
5. **Cases of §F.1's list that this suite does not run.** Each attacks another track's code, or code that does not
   exist in R1.0 yet; it belongs in its owner's tests or in a `tenancy-cases/<track>.ts` file:
   - the render cache with the same slug in two stores, and a suspended store's pageKey refusing orders (T3's serving
     and public order path, `public-api-security.ts`);
   - a client-sent `x-sg-path` on a public route (T3; the upload-route case is here);
   - a preview token forged with A's page id and B's store id (T3's token format);
   - 60 signups from rotating /64s, and 10 parallel accepts of one invite (T2; `acceptInvite` is a stub here);
   - `addImpersonationNoteAction`, the store-side `replay(ctx, id)` of the outbox and `registerBudgetProfile`: none of
     them exists in this tree; they arrive after R1.0.
