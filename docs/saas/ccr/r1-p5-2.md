# r1-p5-2: per-store Sheets run history rows in `cron_cursors` (`sheets.push:<storeId>`)

- Status: open (a note: nothing in P8's runner forbids the rows today; P8 confirms or answers)
- Filed by: P5 · Owner: P8 (`src/lib/jobs/**`, the job runner, housekeeping and the store purge)
- Files P5 writes: `src/lib/sheets/history.ts` (P5). Files P8 may touch: `src/lib/jobs/scope.ts`, the housekeeping job, the
  purge plan.

## What

OPE-§19.8 and OPE-§L keep "the last 20 `SheetsRunReport`s per store, ≤ 4 KB, in `cron_cursors.state` of `sheets.push`
per store". The runner has one row per job and no per-store state (`src/lib/jobs/scope.ts` reads and writes only
`cursor`), so P5 keeps one row per store:

| `job` | `cursor` | `state` | `updated_at` |
|---|---|---|---|
| `sheets.push:<storeId>` (≤ 38 chars, inside `JOB_RE`) | `""` | `{ v: 1, runs: SheetsRunReport[] }`, newest first, ≤ 20 runs, ≤ 4 KB | the last recorded run |

A run holds counts, a duration, the trigger and a cause code (`src/lib/integrations/causes.ts`), never a customer field,
a sheet id or raw error text. The key is built from the scope's store id only.

`activeSheetsStores()` (the platform count of the core §H.5 backlog threshold `max(15, 5 × ceil(active / 16))`) counts
these rows with `updated_at` in the last hour (`job LIKE 'sheets.push:%'`, primary key range, cached 5 minutes under the
platform key "p"). It reads no row's content and touches no tenant table, so no `// tenancy: platform` annotation and no
pin is needed.

Step 4 (the push runner) will also keep the 429 breaker in the `state` of the job row `sheets.push` itself (OPE-§19.7:
"`cron_cursors.state` of `sheets.push` + an in-memory copy"); the runner writes only `cursor` there.

## Asks

1. Keep the runner's own reads and writes on the job's exact name (`WHERE job = ?`), never a prefix, so a
   `sheets.push:<id>` row is never taken for a job or its cursor; never write `state` of a job row it does not own.
2. Store purge (core §A.5, `purgePlan()`): delete `cron_cursors` row `sheets.push:<storeId>` with the store (the table
   has no `store_id`, so no FK removes it). Housekeeping may also drop rows whose `updated_at` is older than 30 days.
3. If the runner ever needs a different place for per-store job state, say so: P5 moves the history behind the same
   functions (`recordSheetsRun`, `sheetsRunHistory`, `activeSheetsStores`), and no caller changes.

## Why not a new table or column

The schema is frozen at 0005 (§D.5) and the spec names `cron_cursors.state`. A row per store costs ≤ 4 KB per Sheets
store (≈ 400 KB at 100 stores) and one primary-key read per Sheets screen view.
