## 1. Delivered (row → files)

**§E.2 seam hardening, §E.4 context** (`src/lib/tenancy/{seam,context,owned}.ts`, `src/lib/platform/seam.ts`,
`src/lib/auth/{grant,gate}.ts`)
- `storeAction`, `userAction`, `platformAction` and `publicAction` check the origin first. A missing `Origin` is
  refused whatever `checkSameOrigin` answers. `storeGuard` checks the origin before the session lookup, for
  state-changing methods only.
- Only actions take the store from the proxy-signed path (`x-sg-path-sig`, constant-time verify in T3's
  `edge/path-sig`). A missing or bad signature answers `not_found` and logs one `path_unsigned` line per minute
  (`error_events` only arrives with 0005).
- The store's "require 2FA" setting (D12) sends a member without TOTP to the enrolment page, or answers
  `forbidden` / `error.member_2fa_required`.
- **Impersonation** (§B.8, D70): the read-only synthetic membership with `scope.kind = "impersonation"`, re-checked on
  every request. The seam checks:
  - the row: this store, this session, this staff member, not ended, not expired (an expired row ends itself);
  - the staff member still has `stores.impersonate` and TOTP, and is inside the IP allowlist.

  Every write key is refused with `impersonation_read_only` and audited `platform.impersonation.write_refused` with
  both identities.
- **Tenant step-up** (§B.7): `stepUpUntil` = `sessions.step_up_at` + 5 min. The §B.7 keys go through `assertStepUp`.
- The `platform_read_only` kill switch refuses writes (§H.8). The `rate` option charges `s:<sid>:<name>[:<userId>]`.
  `last_active_at` is touched at most every 10 minutes.
- The `WriteCtx` overloads (D71) narrow in two places only: `storeAction` and `memberWriteScope`.
- `assertOwned` and the §E.4 `runAsIdentity` test context are included. It refuses to run in production.

**§B identity** (`src/lib/auth/**`)
- **Sign-in** (`login.ts`, `attempts.ts`, `turnstile.ts`):
  - three `p:` buckets: IP 10/15 min, account on this network 5/15 min (refuses that network), account everywhere
    20/15 min (challenge only, never refuses);
  - past 3 failures a Turnstile challenge, which costs no account budget;
  - unknown e-mails burn a full scrypt run. Unknown, wrong password and banned all get one generic `invalid`.
- **Password hashing** (`password.ts`): scrypt behind a semaphore (2 running, 16 waiting, 4 s), then `busy`.
- **Sessions** (`session.ts`, `landing.ts`): a hashed 256-bit token, rotated on sign-in completion and on privilege
  changes (the step-up and the view-as never survive a rotation). Also the switcher data, the agent `/queue`
  landing, and the last store remembered.
- **Signup** (`signup.ts`, `stores.ts`, `platform-invites.ts`, `identity.ts`, `platform-config.ts`):
  - all five modes, the `signups_enabled` kill switch, and the D9 default rule;
  - the Turnstile gate in approval / open (D69);
  - the daily sandbox ceiling, charged before the transaction and refunded on any rollback (CRIT2-12);
  - one generic sentence for a taken e-mail or handle;
  - platform invite codes consumed by a conditional update;
  - `identity_links` net/device rows, at most 20 per kind.
- **Step-up** (`step-up.ts`): TOTP (`p:mfa:stepup`) or, for a tenant without TOTP, the password (`p:password`).
  Refused under impersonation. An account with TOTP can only step up with TOTP.
- **Reset links** (`users.ts`, `reset.ts`): staff-issued, 60 minutes, single use by a conditional update. Every
  session ends after the reset.
- **Bootstrap** (`bootstrap.ts`): first super_admin under a named lock. `SETUP_TOKEN` is compared digest against
  digest with `safeEqual`.
- **PLA Q.19 user functions:** `deleteUserAccount(ctx: UserCtx | PlatformCtx, target?)` with the `owns_store` /
  `is_staff` refusals and the step-up, `stepUpWithPasswordAction`, `leaveStore`, and the scoped member and invite
  reads.
- **Mailer** (`src/lib/mail/**`): optional SMTP, with templates in ar/fr/en.
- **Identity catalog**: `src/lib/auth/i18n/{en,fr,ar}.ts`.

## 2. Step 4: security self-review

I reviewed the whole `5bbef59..HEAD` diff against the six themes of the step. Two findings were fixed (marked
**fixed** below). Everything else held.

**CSRF / Origin order**
- Every wrapper checks the origin before any session, store or DB work: `storeAction`, `userAction`,
  `platformAction`, `publicAction`, `stepUpWith*`, the 2FA actions, `logout`, `setLocaleAction`, `verifyAction`,
  `switchAccountAction` and `endImpersonationAction`.
- `storeGuard` skips the check only for GET, HEAD and OPTIONS.
- `acceptInviteAction` reads the signed-in user before `publicAction`. That is a read, and the write happens only
  inside the wrapper.
- `setupAction` checks the admin gate before the origin, on purpose: the gate's 404 hides the page.

**Token hashing**
- Session, invite and reset tokens are `newToken(32)` and stored as sha256 hex. Platform invite codes use a keyed
  hash.
- The raw token only exists in the cookie or the URL that is shown once. The selftests check that it never reaches
  the row or the audit.

**Timing-safe compares**
- Passwords use scrypt with `timingSafeEqual` and the same length. `SETUP_TOKEN` uses `safeEqual` over digests.
- Tokens are looked up by their hash, so there is no secret string compare.
- The path signature is T3's constant-time verify.
- Unknown e-mails at sign-in burn a scrypt run inside the same semaphore.

**Session fixation**
- A sign-in deletes the browser's previous session and issues a new token.
- The second factor rotates the pending session into a new one.
- Enabling or disabling 2FA, changing the password and "sign out others" rotate the session.
- An invite accept that creates a new account issues a new session.
- Step-up and view-as never carry over a rotation.

**Enumeration through different errors**
- Sign-in answers one `invalid` (the buckets are keyed the same for unknown e-mails).
- Signup answers one sentence for a taken e-mail or handle.
- Creating an invite answers the same for any e-mail.
- An unknown, used, revoked or expired invite or reset link reads the same.
- A store answers the same `not_found` / 404 for no store, no membership or a closed door.
- The remaining differences (`wrong_account`, `sign_in_first`) need a valid invite token, so they tell the token
  holder nothing they couldn't see on the page.

**Role escalation through invites**
- At creation, `invitableRoles` never returns a role at or above the inviter (owner excepted). `changeMemberRole`
  applies the rank rule on both the target and the new role. An existing member's accept never changes their role.
- **Fixed:** a pending invite outlived its inviter's demotion or removal. For example, an admin invites a manager,
  the owner demotes the admin to viewer, and the link still made a manager. `acceptInvite` now re-checks the inviter
  inside the locked transaction, before the conditional update: the inviter must still be an active member and the
  role must still be in their `invitableRoles`. Otherwise it answers the one `team.invite.invalid` and writes nothing,
  not even the new account.
- **Fixed:** §H.8 says `signups_enabled` off also closes the invite-accept form. `acceptInvite` ignored it. It now
  answers `closed` / `team.invite.closed` while the switch is off, and the invite page shows "Invitations are paused"
  in place of the form. The link keeps working once the switch is back on. The new keys `team.invite.closed_title`,
  `team.invite.closed` and `error.closed` are in ar/fr/en.

## 5. Deviations (kept, with reasons)

1. **Inviter re-checked at acceptance** (step 4). This is stricter than the letter of §B.5, which checks the role
   only at creation. Without it, a pending link outlives its inviter's demotion or removal, which is the
   escalation path the review was asked to close. The effect: when an inviter is removed, their pending links stop
   working, and the owner sends new ones.
2. **New action code `closed`** for the invite accept under `signups_enabled` (with `team.invite.closed`). README
   §"When to file one" allows a part's own code.
3. **`path_unsigned` is a rate-limited server log line**, not an `error_events` row, until 0005 brings the table
   and `recordError` (step 1).
4. **T1 stubs read as defaults:**
   - seat gauges and the `invites` feature: no limit, logged once;
   - the D69 ceiling: skipped, logged once;
   - kill switches: none tripped;
   - settings: schema defaults.

   A real read error still throws, so no write is let through on a failed read (CCRs r1.0-t2-3 and -6).
5. **The account lock columns** (`failed_logins`, `locked_until`) are no longer read or written (no hard lock,
   SEC-22). They are dropped in 0006.
6. **The README lists `src/lib/tenancy/seam.ts` and `src/lib/platform/{seam,impersonation}.ts` as maintainer
   files.** The §K.1 T2 row gives them to T2, so I followed the row.
