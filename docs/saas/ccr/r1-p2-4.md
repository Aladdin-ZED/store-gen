## 3. Maintainer: the tenancy harness

### 3a. `src/app/app/actions.ts` is not a store action file

`NOT_STORE_ACTIONS` (`scripts/qa/tenancy-check.ts`) lists `src/app/app/account/actions.ts` and
`src/app/app/new/actions.ts` but not PLA-§M.1's `src/app/app/actions.ts`, whose two exports are `userAction`s with
no store (`setLastStoreAction`, `acceptLegalAction`). Without the entry, `test:tenancy` reports 2 failures ("…has an
attack case") and `qa:action-replay` 2 more ("…has a recorded body"); a store action case cannot hold them (the
member of both stores may legitimately pick A, so "B's path with A's ids ≡ a missing id" is false by design).

```diff
   "src/app/app/account/two-factor/actions.ts": "the account's own two-step setup (T2): no store",
+  "src/app/app/actions.ts": "the signed-in user's own picker hint and legal re-acceptance (P2, userAction): no store; attacked in tenancy-cases/shell.ts (the user actions)",
   "src/app/app/new/actions.ts": "a new store (T2): the caller is a member of nothing there yet",
```

P2's special case "shell: the user actions (no store)" proves what the generic suite would: A's store id answers as
an unknown one and nothing is remembered, a store id inside the input is refused, nothing pending is accepted, and a
staff session viewing A is refused (`impersonation_read_only`, audited without a store) with A unchanged.

(Optional, later: `src/lib/auth/actions.ts` keeps T2's older `setLastStoreAction`; P2's picker moves to the new one at
p2-10 and the maintainer may then retire T2's.)

### 3b. `qa:action-replay`: "A's owner's own call works" for actions bound to a state or to a stub

The replay requires A's owner's call with the victim body to answer `ok: true`. Some P2 cases cannot, by design:

| Case | A's owner's answer | Why |
|---|---|---|
| `submitForReviewAction`, `answerReviewQuestionAction`, `submitAppealAction` | `review_closed` | the fixture's A is `active`; the card belongs to `pending` / `needs_info` / `rejected` |
| `reopenOwnStoreAction` | `invalid` | A is not closed (T1's rule) |
| `closeOwnStoreAction` | `invalid` (typed handle) | the case never closes A: the rest of the run reads A |
| `snoozeHealthIssueAction`, `unsnoozeHealthIssueAction`, `createStoreRequestAction`, `withdrawStoreRequestAction` | `unavailable` | P1's stubs (build note item 14), until P1 merges |
| `modeSwitchPlanAction` | `unavailable` | P3's `landingModeSwitchPlan` stub, until P3 merges |
| `requestStoreExportAction` | `unavailable` until P8's export API is in the tree | P8's stub |

Proposed (the harness's call): a `TrackActionCase.live?: { expect: string; why: string }` the replay checks instead
(`refusal(live) === expect`, the `why` listed with the not-applicable rows), or an `unavailable` answer classified
like a typed stub (not applicable, "pending <track>") rather than a failure. `test:tenancy` itself is unaffected: its
role matrix accepts these answers as "reaches the body".

### 3c. (Optional) writes a viewer may make

Eleven P2 writes take a key the viewer holds (`pages.read`: mint and revoke a private preview link; `store.read`: the
review card's three, the health recompute, read marks, the reveal report, skip, reopen). With `write: true` the
harness's "member of both stores on A's path (A's viewer)" step passes the seam for real: it runs the body (a
preview link, the recompute) and, the first time that member reaches A that day, the seam's
`store_members.last_active_at` touch changes A's fingerprint ("A's rows unchanged by every attempt ·
[store_members]", seen on the first such case), while the step checks nothing for a key the viewer holds. So their
cases say `write: false` and P2's special case "writes under a read key" proves their impersonation refusal (and the
audit row per call). A `viewerMay?: true` flag that skips only that step, or a fingerprint that ignores
`store_members.last_active_at`, would let the cases say `write: true` (and get the generic "staff viewing A: refused"
check back).

## 4. P1: who writes which audit row

## 5. Notes for the spec (no code change asked)

- **Operation de-duplication bucket.** PLA-§L writes `p:op:<userId>:<opId>`; the bucket helper refuses ":" inside a
  key, so P2's step-up actions spend `p:op:<userId>.<opId>` (10 min). Same meaning.
- **`recomputeHealthAction`'s bucket.** PLA-§M.1 writes `storeAction("store.read", …, { rate: { name:
  "health:recompute", limit: 6, windowSec: 3600, per: "store" } })`. The seam charges `opts.rate` before the body, so
  a support view (refused in the body: the key is a read) would spend the store's bucket. P2 charges the same bucket
  (`s:<sid>:health:recompute`, 6 / h, the whole store) in the body after the refusal.
- **Writes under a read key and `platform_read_only`.** Core §H.8 refuses every `storeAction` write while the switch
  is on; the seam enforces it for write keys only. P2's writes under `store.read` / `pages.read` (the review card,
  preview links, the recompute, read marks, the reveal report, skip, reopen, leave) check it in the body
  (`guardReadKeyWrite`), with the impersonation refusal and its audit row.
- **`landing.inStoreMode` "in the same transaction".** PLA-§22.2 / core §A.2 rev 3 ask `useDirectionAction` to set it
  in the page's transaction; T4's `createPageFromDirections` takes no transaction. P2 sets it (audited
  `store.landing_settings.updated { reason: "onboarding" }`) **before** the page exists, so the draft is never hidden
  behind the store's 404 even if the page write then fails.
