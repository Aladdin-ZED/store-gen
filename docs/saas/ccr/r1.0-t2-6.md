# r1.0-t2-6: the D69 counter must exist in R1.0; the T1 stubs identity reads as defaults

- Status: open
- Filed by: T2 · Owner of the files: T1 (and the maintainer for the table)
- Files: src/lib/tenancy/usage.ts, src/lib/settings/index.ts, src/lib/tenancy/handles.ts, src/lib/tenancy/entitlements.ts; src/lib/db/schema.ts + drizzle (maintainer)

## What

1. **`platform_usage` in R1.0.** T2's signup charges `chargePlatformUsage("pending_stores", <platform day>, 1, {
   limit: platform.signup.pendingStoresPerDay })` before its transaction and `refundPlatformUsage` after a rollback
   (§B.2 steps 6-7, D69, CRIT2-12). The table is cut in 0005 (§D.5), so a real body would hit `ER_NO_SUCH_TABLE` in
   R1.0 and refuse every invite-mode signup with `server` (R1.0 exit criterion 5 signs a user up with an invite code).
   Either the maintainer adds `platform_usage` (§D.5 shape, `period varchar(10)`: the day key is `YYYY-MM-DD`, C0a
   drift item 2) to 0004 now, or T1's body keeps throwing the stub message (`not implemented: T1 …`) until 0005, which
   T2 reads as "no counter" (the ceiling is skipped and logged once). Please pick one before the R1.0 integration.

2. **Stub messages identity reads as defaults.** Until T1 merges, T2 treats exactly an error whose message starts
   with `not implemented: T1` as the 0004 default (src/lib/auth/platform-config.ts `isT1Stub`) for:
   - `getPlatformSetting("platform")` → `PlatformSettingSchema.parse({})`; `getPlatformSetting("platform_turnstile")` →
     the env TURNSTILE_* keys (the registry defaults);
   - `activeKillSwitches()` → no switch tripped (also CCR r1.0-t2-3);
   - `handleProblem()` → the format, `RESERVED_HANDLES`, ADMIN_GATE and `platform.reservedHandles`;
     `checkHandleAvailable()` → skipped (the unique index refuses a taken handle at insert);
   - `chargePlatformUsage()` → no counter (item 1).

   Any other error propagates. Keep the prefix until each body lands; once T1 merges, T2's fallbacks are dead code that
   the maintainer may delete at integration.

3. **`handleProblem` reads `platform.reservedHandles` synchronously.** Its frozen signature is sync, but the setting
   is an async cached read. T2 calls it as written; if T1 needs the setting inside, please keep the sync signature by
   reading the 30 s cache (and answering `reserved` on a cold cache only when the static list matches).

## Why

Without (1) the R1.0 signup either breaks or silently has no ceiling; (2) keeps `main` signing users up between the
T1 and T2 merges without a failed read ever opening a gate.

## Effect on others

(1) is a schema change (maintainer). Nothing else: the signatures are unchanged.
