# r1-p3-12: mount the attestation sheets and "Publish this page" in the builder; the inbox's shell hooks

- Status: open (filed at P3 wave 1, step p3-w1-pages-leads-screens). Applied at the P6 and P2 wave 1 merges (or by
  p3-w1-verify when the modules are there). Nothing breaks while it is open: the attestation actions and sheets work
  on their own, "Publish this page" opens the drafts list outside the builder, and the inbox works without the pulse.
- Filed by: P3 LANDING · Owners of the files: P6 (the builder under `src/components/builder/**`, the editor route),
  P2 (`src/components/admin/shell/**` outside the track files, the pulse client)

## What

1. **Attestation sheets (LAN-§6.1, §6.4 rule 7, Q31).** The builder mounts P3's two sheets beside each other:
   - `ProofAttestSheet` (`src/components/admin/landing/proof-attest.tsx`) when the owner clears `sample` on a visible
     `reviews` / `socialProof` / `stats` / `beforeAfter` section, or types or changes `product.rating`;
   - `FactAttestSheet` (`src/components/admin/landing/fact-attest.tsx`) for the soft numbers finding's fix
     `{ actionId: "landing:attest-fact", field: path }`.

   The builder's server page passes `attestProofAction` / `attestFactAction` of `src/app/app/[store]/pages/actions.ts`
   as the `action` prop. Confirm writes the audit row (`page.proof_attested`, `page.fact_attested` with
   `source: "owner"`), then `onConfirmed` clears the flag and re-runs the check; Cancel keeps `sample: true`.

   ```tsx
   <ProofAttestSheet open={!!proof} pageId={page.id} subject={proof} action={attestProofAction}
     onConfirmed={(s) => { clearSample(s); setProof(null); }} onCancel={() => setProof(null)} />
   <FactAttestSheet open={!!fact} pageId={page.id} fact={fact} action={attestFactAction}
     onConfirmed={() => { setFact(null); recheck(); }} onCancel={() => setFact(null)} />
   ```

2. **⌘K "Publish this page" (LAN-§23.9).** P3's command (`landing.publish`, `pages.publish`) dispatches
   `window.dispatchEvent(new CustomEvent("sg:command", { detail: { id: "landing.publish", pageId } }))` while the
   path is `/app/<h>/pages/<id>/edit`. The builder listens and opens its publish dialog for that page:

   ```ts
   useEffect(() => {
     const on = (e: Event) => {
       const d = (e as CustomEvent<{ id: string; pageId: string }>).detail;
       if (d?.id === "landing.publish" && d.pageId === page.id) openPublishDialog();
     };
     window.addEventListener("sg:command", on);
     return () => window.removeEventListener("sg:command", on);
   }, [page.id]);
   ```

3. **Inbox freshness (LAN-§10.6 "≤ 2 s after its beacon, one pulse at most").** When the pulse client (P2) sees
   `leadsNew` or `waIntentsNew` change while `/app/<h>/leads` is open, it calls `router.refresh()` (one refresh per
   pulse). P3's contributor already publishes the counters (`src/lib/pulse/contributors/landing.ts`).

4. **Chord `G L`.** P3's jump command `landing.leads` carries `shortcut: "G L"`; P2's chord handler reads
   `CommandDef.shortcut` (it carries no other chord today).

5. **The address card.** The pages list shows a local stand-in (`src/components/admin/pages/pages-address.tsx`) until
   P2's `AddressCard` is on the branch; p3-w1-verify swaps it for
   `<AddressCard compact store={…} live={homeLive} pageId={homeId} slots={{}} />` (the slots stay empty until wave 2).

## Why

The sheets and the command are P3's (LAN-§26.1); their mount points are in P6's builder and P2's shell, which P3 may
not edit (§K.3). The inbox's live update rides on P2's pulse (core D46).

## Effect

No contract changes. The builder gains two mounts and one listener; the pulse client gains one refresh rule.
