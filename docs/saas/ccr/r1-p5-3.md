# r1-p5-3: how P5's health rules read beyond `HealthInputs`, and what `test:health` must keep

- Status: open (a note for P1's `test:health`, `test:health-db` and `platformFlags`; no change to a frozen file)
- Filed by: P5 · Owner: P1 (`src/lib/health/{engine,inputs,platform-flags,selftest}.ts`, `scripts/qa/health-db-check.ts`)
- Files: `src/lib/health/rules/integrations.ts` (P5)

## What P5 ships

`rules/integrations.ts` exports six rules and one `HealthRuleFixture` per rule (P0b CCR P5-8):

| Rule | Group | Sev | Evidence `metric` | Data |
|---|---|---|---|---|
| `int:sheets_backlog` | integrations | 3 | `sheets_oldest_pending_min` (baseline = the scaled threshold) | `inputs.sheets`, `inputs.integrations` + the platform count `activeSheetsStores` |
| `int:capi_failing` | integrations | 2 | `capi_failing_pixels` | `inputs.integrations` |
| `int:telegram_failing` | integrations | 2 | `telegram_failures` | `inputs.integrations` |
| `int:delivery_dead` | integrations | 2 | `outbox_dead` | a scoped count of the store's dead deliveries |
| `int:turnstile` | integrations | 1 | `captcha_failed_share` (minN 20) | a scoped count of two store-local days of orders |
| `conv:trigger_hint` | conversion | 1 | `confirmed_share` (minN 30) | `inputs.orders` (P4's `orderKpis` 28 d), `inputs.settings.conversions` |

Three rules read data `HealthInputs` does not carry (the brief and OPE-§27.2: `collect` is "read-only, scoped,
≤ 40 ms"). They load the server reads lazily (`await import(...)`), because the registry is imported by P1's offline
`test:health` too and the reads are `server-only`; a failed import or query leaves the rule silent. A fixture supplies the
same data under an extra inputs key, `p5Reads` (built with `withReads(inputs, reads)`), so every P5 fixture runs offline.

## Asks to P1

1. **Merge fixtures by spread** (`{ ...base, ...fixture.fires }`, as the `HealthRuleFixture` comment says), so the
   `p5Reads` key reaches `collect`. A merge that keeps only the declared `HealthInputs` keys would make
   `int:sheets_backlog`, `int:delivery_dead` and `int:turnstile` silent on their `fires` fixture.
2. **Fixtures set `now`.** Two P5 rules judge time (`int:capi_failing`: an error in the last 24 h; `int:turnstile`: the
   store-local day), so P5's fixtures carry `now: 2026-10-28T10:00:00Z`; the base inputs' `now` is overridden by them.
3. **`platformFlags` (PLA-§6.3.3, PD79)** derives `sheets_backlog`, `capi_failing`, `telegram_failing` and `outbox_dead`
   from the issues above by id (`int:sheets_backlog`, `int:capi_failing`, `int:telegram_failing`, `int:delivery_dead`);
   `sheets_error` reads `sheetsBacklog(scope).lastRunFailedAt` (filled from the run history, `src/lib/sheets/history.ts`).
4. **`test:health-db` (two stores)** runs P5's rules with their real reads: run it under
   `--conditions=react-server` (as `test:integrations-db` does) or stub `server-only`, else the three rules above stay
   silent there. P5's own DB proof of the same rules on two seeded stores is `scripts/qa/integrations-db-check.ts`
   section 5.

## Optional (later)

If P1 prefers one read pass, `HealthInputs` could gain `outbox: { dead: number } | null` and
`captcha: { today; yesterday } | null` filled by `deadDeliveryCount` / `captchaDays` (`src/lib/integrations/health.ts`);
the rules already prefer given data over their own read, so they would switch with a one-line change each.
