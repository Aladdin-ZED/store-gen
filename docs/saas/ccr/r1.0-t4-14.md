# r1.0-t4-14: `qa:action-replay` runs in process on a throwaway database: list it with the DB-backed tests

- Status: applied in 7ffbc8c: `test:db` runs `qa:action-replay` after `test:tenancy`; `test:e2e` no longer does.
- Filed by: T4 · Owner of the file: maintainer
- Files: package.json

## What

```diff
-    "test:db": "npm run test:migrate && npm run test:tenancy && npm run test:pixels-publish && npm run test:public-api && npm run test:php",
+    "test:db": "npm run test:migrate && npm run test:tenancy && npm run qa:action-replay && npm run test:pixels-publish && npm run test:public-api && npm run test:php",
…
-    "test:e2e": "npm run qa:headers && npm run qa:edge-sim && npm run qa:action-replay",
+    "test:e2e": "npm run qa:headers && npm run qa:edge-sim",
```

`gate:tenancy` keeps `qa:action-replay` as it is.

## Why

`scripts/qa/action-replay.ts` (T4, §F.1) needs no running server: it creates, migrates and drops its own
`cod_test_*` database and replays every exported server action in process, through the request-context seam (§E.4)
inside Next's request stores, like `test:tenancy`. In `test:e2e` it would run after `npm run build` for nothing; in
`test:db` it runs with the other DB-backed suites and fails the gate where they do. The HTTP transport the spec
describes (recording `Next-Action` ids in a browser against `next start`) is the R1.0 integration's to add, on top of
the same bodies (`ACTION_CASES` in `scripts/qa/tenancy-check.ts`).

## Effect on others

- None on frozen contracts.
- `npm run gate` runs the replay once (in `test:db`) instead of in `test:e2e`; it takes about 40 s on XAMPP.
