- Status: open (filed at P3 wave 2, step p3-w2-wa-order). For the P3 wave 2 merge. Until it lands: `render-check`
  (`test:render`, in `npm test`) reports the `assist` chunk and the page composition over their budgets (the same
  situation as CCR r1-p3-9 at wave 1); `test:landing-addons` holds `assist` to the budget asked for below; "Set
  phone" links a form lead through the adapter of item 2; the intent API shares the `lead` burst scope; and
  `test:public-api` fails its four `/wa` cases that expect an intent (the fixture stores never turn the setting on:
  item 3), while its "take_orders false" case passes.
- Filed by: P3 LANDING · Owners of the files: maintainer (`src/landing/runtime/budgets.json`, `src/lib/db/schema.ts`
  and its migration, `scripts/qa/public-api-security.ts`, `src/lib/security/burst-limit.ts`), P5 (the `wa_order_reply`
  template kind).

## What

1. **`assist` and the page cap (LAN-§11.2, §5.2; `src/landing/runtime/budgets.json`).** The chunk now carries the
   LAN-§11.3 serialiser (≈ 770 B gz alone) and the intent click (fetch, 4 s fallback, in-app rule, the 30 s reuse, the
   ready line): measured with the asset build's own esbuild options (es2019, minified, gzip -9) the chunk goes from
   2,691 B to 3,909 B. It was already at its 2,600 B budget before LP-11 (2,691 B, inside the +5 % tolerance).

   ```diff
   -  "assist": 2600,
   +  "assist": 4000,
   ```

   and, for headroom, the page composition cap (`page`, the scripts of one landing document with `assist`) by the same
   ≈ 1,250 B: render-check measures 35,361 B against 34,800 (inside its +5 %, but the asset build warns "over the 34.0
   KB cap"): `34800 -> 36100`. Today render-check fails one line on P3's branch: "runtime assist is 3909 B gzip, over
   its 2600 B budget + 5%".
   Note for the `//` line: "assist 2600 -> 4000 and page 34800 -> 36100 (CCR r1-p3-14, measured 2026-11-07: 3,909 B):
   Order on WhatsApp (LP-11) bundles the LAN-§11.3 serialiser and the intent click into `assist`." Pages of a store
   with the setting off pay the bytes too (one chunk per add-on, AddonChunk frozen at C0a); a separate `assist-wa`
   chunk would need a new AddonChunk name and a budget key, which is a bigger change for 1.2 KB.

2. **`leads.merged_into` (LAN-§10.3 "Set phone", LAN-§2.1).** `src/lib/db/schema.ts` `leads` and a guarded migration:

   ```diff
   +    /** "Set phone" (LAN-§10.3): the WhatsApp intent this form lead is the same person as */
   +    mergedInto: id26("merged_into"),
   ```

   Until it lands, `setLeadPhone` (src/lib/leads/write.ts) links the form lead with `status = 'lost'`,
   `lost_reason = 'merged'` (the inbox shows "Same person as a WhatsApp request") and no follow-up. After it, P3 adds
   `merged_into = <intent id>` in the same UPDATE (one line) and the sheet links the two rows.

3. **The harness (`scripts/qa/public-api-security.ts`, the `/wa` cases).** The route answers `unavailable` unless the
   store turned `landing.waOrder.enabled` on and a WhatsApp number exists (the page's form number, else the store's
   `store.whatsapp`): an intent without a number to open would be a dead end, and a store that never offered the
   button should not collect intents from crafted requests. Before the `/wa` cases, for stores A and B:

   ```ts
   for (const sc of [tA.scope, tB.scope]) {
     await updateStoreSetting(sc, "landing", { waOrder: { enabled: true } }, { id: "system", ip: null });
     await updateStoreSetting(sc, "store", { whatsapp: "+212661000000" }, { id: "system", ip: null });
   }
   ```

   plus one case: setting off → `unavailable`, nothing stored.

4. **A `wa` burst scope (`src/lib/security/burst-limit.ts`).** The route uses `burstLimit("lead", ip)` (60 / min, the
   database floor `p:wa:ip:<h>` 30 / 10 min behind it). Optional: `wa: { limit: 60, windowSec: 60 }` and P3 switches
   the one call.

5. **P5's `wa_order_reply` kind (LAN-§11.5).** The inbox's "Copy reply" reads the owner's active `message_templates`
   row of kind `wa_order_reply` (`ownTemplate`, src/lib/landing/templates.server.ts), else the defaults in
   `WA_ORDER_REPLY` (src/lib/landing/templates.ts, ar / fr / en, vars `{ref}` `{offer}` `{total}`). P5 registers the
   kind in its templates screen with those defaults so owners can edit it.

6. **Audit label.** `lead.phone_set` (meta `{ leadId, merged }`, never the phone): the shell's activity label "Set a
   WhatsApp request's phone" (fr "A ajouté le téléphone d'une demande WhatsApp", ar "زاد الرقم ديال طلب واتساب").

## Why

LP-11 (LAN-§11): the intent is priced on the server (`priceWaSelection`, no second pricing engine), stored as a
`kind = 'whatsapp'` lead and finished by the team in the inbox. Items 1 and 3 keep the suites green after the merge,
item 2 replaces an adapter with the column the spec names, items 4 to 6 are small hygiene.

## Effect

No behaviour change for stores with the setting off (no `wo` data, today's HTML). With it on, live pages get the
upgraded link. Files P3 changes after the merge: `src/lib/leads/write.ts` (one line, item 2),
`src/lib/wa-order/create.server.ts` (one word, item 4).
