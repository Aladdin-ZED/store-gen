# r1.0-t4-12: how a publish-gate refusal reaches the builder, and the slug-history rows T3's route reads

- Status: open
- Filed by: T4 · Owner of the files: T3 (`publish.server.ts`, the store slug route), maintainer (`prepublish.ts`), T2 (`seam.ts`)
- Files: src/lib/render/publish.server.ts, src/lib/render/prepublish.ts, src/lib/tenancy/seam.ts, src/app/s/[store]/[slug]/**

## What

1. **A typed refusal error** (maintainer, `src/lib/render/prepublish.ts`), so the frozen
   `publishPage(scope, pageId, opts): Promise<PublishResult>` can refuse without a new return shape:

   ```ts
   export class PrePublishRefused extends Error {
     constructor(readonly code: PrePublishCode, readonly items: GateItem[]) {
       super(`publish refused: ${code}`);
       this.name = "PrePublishRefused";
     }
   }
   ```

2. **T3**: when `runPrePublishChecks(ctx)` answers `{ ok: false, code, items }`, scoped `publishPage` (and the slug-move
   republish, which calls it) throws `new PrePublishRefused(code, items)` before the version row is written.
3. **T2**: `storeAction`'s error mapping (`seam.ts`, next to `QuotaError`) answers it as the §E.2 result:
   `if (err instanceof PrePublishRefused) return { ok: false, error: err.code, items: err.items };`.
4. **T3, slug route** (LAN-§15.1, `page_slug_history`): T4 writes the rows from `src/lib/editor/slug-history.ts`
   (`recordSlugMove(scope, pageId, oldSlug)`, called by the builder's slug move in `pages.server.ts` `updateMeta`):
   - `(store_id, slug)` = the page's old slug, `page_id`, `until` = move time + 12 months, `hits` = 0;
   - only for a page that was ever published (`first_published_at` or `published_version_id` set);
   - the page's current slug never has a row (moving back, another page taking the slug and `revertSlug` after a
     failed republish delete it).

   The route needs only: `WHERE store_id = ? AND slug = ? AND until > NOW()`, then 308 when that page is published.

## Why

§M.1 rule 2 and D51: "a failure returns through `storeAction` as `{ ok: false, error: code, items }`; the publish
dialog renders one row per item". The frozen `publishPage` returns `PublishResult`, so a refusal has to be thrown, and
nothing in C0a names the error. The builder (`src/lib/editor/actions.ts`) already accepts both forms without waiting:
any thrown error whose `code` is `budget_blocked` / `honesty_blocked` / `design_blocked` and whose `items` are
`GateItem[]` (it catches inside its seam call, so (3) matters for other callers such as the pages list), and a seam
result with that `error` and `items`. The publish dialog lists the hard items, then the soft ones, each with its fix
(`fix.sectionId` / `item.sectionId` selects the section, a known `fix.tab` opens the panel), titles through the admin
catalog (`t(item.title, item.vars)`), with a plain fallback line per gate while a key has no catalog entry.

(4) records what the rows mean so the 308 and the history writer agree (LAN Q22).

## Effect on others

- None on frozen signatures: (1) is a new export, (2) uses the existing `throws` of `publishPage`, (3) one more branch.
- P3 / P6 / the core budget gate: their `GateItem.title` / `detail` keys render as soon as they are in the catalog.
