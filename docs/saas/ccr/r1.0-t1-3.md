## 1. The legal seed has no data file and no marker key (maintainer)

§H.4 step 5 seeds the legal templates from `LEGAL_SEED_VERSION` / `LEGAL_SEED` in
`src/lib/platform/data/legal/index.ts`, with the marker `legal_seed_v<LEGAL_SEED_VERSION>`. The file does not exist, no
R1.0 row owns it ("P1 owns the file from R1"), and the platform registry cannot declare a key per version.

Proposed:

```ts
// src/lib/platform/data/legal/index.ts (R1.0 content; P1 owns the file from P0)
export type LegalSeedKind = "tos" | "privacy" | "aup" | "dpa" | "store_privacy" | "store_terms" | "store_shipping" | "store_returns" | "store_contact";
export interface LegalSeedDoc { kind: LegalSeedKind; locale: "ar" | "fr" | "en"; title: string; body: string; summary: string | null }
export const LEGAL_SEED_VERSION: number = 0;
export const LEGAL_SEED: readonly LegalSeedDoc[] = [];
```

```ts
// src/lib/settings/keys/markers.ts: one marker holding the last seeded version (0 = none)
export const LegalSeedMarker = z.number().int().min(0);
// src/lib/settings/platform-registry.ts
legal_seed: def({ schema: LegalSeedMarker, secret: false, defaults: () => 0 }),
```

Then T1 adds the boot step in `runBootTasks` (between the protected brands and the flags): when
`LEGAL_SEED_VERSION > legal_seed`, every entry is inserted as version 1, status `draft`, `needs_legal_review = 1`, with
`INSERT IGNORE` on `ld_kind_loc_ver_uq`, then the marker is written last. Until then `boot-tasks.ts` lists it under
"not yet". `syncPromptVersions()` (P7, R1 product) joins the same list when its file exists.

## 2. §D.3 levels that differ from the schema (maintainer, document only)

`test:migrate` (e) compares the tenant tables of `schema.ts` with the §D.2 / §D.3 rows (ENGC-31), and two rows differ:

| Table | §D.3 says | schema.ts has | Proposed §D.3 row |
|---|---|---|---|
| `legal_acceptances` | P (grouped with `legal_documents`) | `store_id` NULL-able (PLA-§2.1: the store whose policy was accepted) | split: `legal_documents` P, `legal_acceptances` P (opt. store) |
| `notification_reads` | P (opt. store) (grouped with `notifications`) | no `store_id` (the read rows hang off the notification) | split: `notifications` P (opt. store), `notification_reads` P |

`TABLE_LEVELS` in `src/lib/db/upgrade-check.ts` already records the schema's levels, and `migrate-check.ts` lists
these two rows as the recorded drift. After the document is fixed, the drift list in `migrate-check.ts` becomes empty.
Every later release that cuts a table adds its level to `TABLE_LEVELS` (the 0005 contract step).

## 3. The single-tenant pixel library migration is no longer called at boot (T4)

§H.4 runs the pixel library migration only inside the conversion (PIX-07). `src/instrumentation.ts` no longer calls
`migratePixelLibrary()`. The conversion runs a port of it for store #1 only, over the store's rows, writing through
`setStoreSetting`. It uses the pure `collectPixels` / `migrationLabel` of `src/lib/pixels/migrate.ts`, which must stay.

Left as it is, the old function would see no `settings.pixel_library` after the conversion (step 5 deletes it) and write
a global library into `settings` again.

Requested:

- delete `migratePixelLibrary` and `libraryMigrated` from `src/lib/pixels/migrate.server.ts`;
- drop the migration section of `scripts/qa/pixels-publish-check.ts` (its import at line 65 and the "migration" block, lines 97-130 at `507fe4e`). `test:migrate` now
  covers the migration on store #1: library order and labels, copied tokens, health `unverified`, interrupted between
  any two of its writes.

One rule changed in the port: `pixel_health` is written before `tracking_secrets`. A run interrupted after the secrets
write finds no token left to copy on the rerun, so with the old order the health of the copied ids was never written.
`test:migrate` catches the old order.

## 4. `forEachStore` is ready for the cron route (T4; note for P8)

`src/lib/jobs/scope.ts` now implements `forEachStore(ctx, opts, fn)`:

- a round robin from the job's cursor (the next store after the last one served, wrapping once);
- a store whose step throws is logged and skipped;
- the budget is checked before each store;
- `where`:
  - `pending_sheets` uses the R1.0 shapes (Sheets enabled in `store_settings.sheets` and a non-test order still
    `pending` / `failed`), ordered by the oldest pending order (ENGC-33);
  - `pending_outbox` and `pending_renders` visit nothing until 0005 creates their tables.

The cursor is kept in process memory until `cron_cursors` exists (0005). The first write after that moves it to the
table. P5 / P8 refine the predicates in place.

## 6. S2 and `settings.home` precedence (maintainer, observation only)

§D.8 sets `stores.home_page_id` from `pages.is_home` (S2), then from `settings.home.pageId` only "when still NULL". Today's
reader (`homePageId()` before C0a) took `settings.home` first. The two disagree only if a single-tenant install has a
flag and a setting that differ. Today's writers keep them in sync (`setHomePage` writes both), so the conversion
follows §D.8 as written and no change is requested.

## 7. Single-tenant readers after the conversion (everyone; hazard)

Step 5 deletes the moved keys (`store`, `defaults`, `sheets`, `pixel_library`, `pixel_health`, `tracking_secrets`,
`turnstile`, `ai`, `home`, `pixels`) from `settings`. From that boot on, any remaining single-tenant

R1.0 build boots on a database with data, which continues the C0a report §8 hazard. The tenancy dry run reports
leftovers in `settings` as a problem once the marker exists.
