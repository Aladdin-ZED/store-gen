## What

`src/lib/jobs/renders.ts` is real from P8 step 5. The frozen signatures are unchanged, and every addition is additive.

### For the tracks that enqueue (P3, P4, P5, P6, the media pipeline)

```ts
await enqueueRenders(scope, "all-live", "store_info");                // P4 saveCallingWindowAction (P3-14), P3 policies / zones
await enqueueRenders(scope, "all-live", "brand");                     // P6 logo / mark / store name
await enqueueRenders(scope, [pageId], "conversions", CONVERSIONS_PRIORITY); // P5 Purchase trigger / per-page override (4)
await enqueueRenders(scope, "all-live", "address");                   // handle rename, S mode on
```

- Call it after the write has committed. A job claimed before the commit would render the old context. A change that
  arrives while a page renders queues a second job (ENGC-4), so nothing is lost either way.
- `enqueued` counts the rows inserted. A page that already has a pending job absorbs the call and keeps the lower
  priority. Ids that are not the scope's live pages are dropped and counted in the error ring (`renders` /
  `foreign_page`).

### For P1's console

| Panel | Call |
|---|---|
| System health › Render queue (PLA-§15.1), `getHealth().renders` | `platformRenderSummary()` (`totals`, `byReason`, `oldestPending` with `slug`, `oldestMin`, `failed24h` with `codes`, `failedOld`, `finishedLastHour`, `throughputPerMin`, `etaMin`, `notes`, `topNotes`, `republish`, `stores`) |
| Alarms (PLA-§15.2) | `render_stuck`: `oldestMin > 60`, or `etaMin === null && totals.pending > 0` on two ticks; `render_failed_old`: `failedOld > 0` |
| Retry for one store (`domains.manage`) | `retryStoreRenders(ctx, storeId, reason?)` → `{ enqueued }` |
| Domains › Re-render progress (PLA-§16.2) | `platformRenderSummary({ reason: "address" })` and its `fanout` (`FanoutProgress`: `stores` / `total`, `pct`, `enqueued`, `failedStores`, `done`) |
| Domains › Re-render all live pages | `enqueueRendersEverywhere(ctx, "address")` → `{ started, fanout }` |
| Domains › Retry failed | `retryFailedEverywhere(ctx, "address")` → `{ started, fanout }` |
| Store profile › Identity & address (PLA-§7) | `renderSummary(platformScope(ctx, storeId))`, `byReason` row `address` |

- Both fan-out requests return at once. One fan-out runs at a time, so a second request answers `started: false`
  with the running one's progress (disable the buttons while `fanout.done === false`).
- The library does not audit. The console actions audit `platform.domains.rerender`, which `AuditAction` does not
  list yet (P1 adds it with its actions).
- `getHealth().renders` (`{ pending, failed, oldestMin }`, PLA-§6) is `totals.pending`, `totals.failed` and
  `oldestMin` of `platformRenderSummary()` (P8 step 11).

### For the integration deploy (§H.10, P0-6)

`enqueueRendersEverywhere(systemCtx("deploy"), "runtime")` re-renders every live page through the cron. It replaces
the `forEachStore → enqueueRenders(scope, 'all-live', 'runtime', 5)` loop of the deploy note, and the request returns
at once.

## Why

PLA-§15.1, PLA-§16.2 and PLA Q.25 name P8's render queue as the data behind these panels, and §H.3 names the tracks
that enqueue. This note gives the exact calls, so no track reads P8's internals.
