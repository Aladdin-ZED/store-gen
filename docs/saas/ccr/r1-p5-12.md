# r1-p5-12: one `integrations.outbox.replayed` row per store-side replay (P5 writes it; P8's `replay` does not for a StoreCtx)

- Status: open (P8 applies it in `src/lib/jobs/outbox.ts` `replay`; P5 codes against today's stub)
- Owner of the change: P8 PLATFORM OPS (`src/lib/jobs/outbox.ts`)
- Asked by: P5 INTEGRATIONS, step 8 (`src/lib/integrations/replay.ts`, `src/app/app/[store]/integrations/actions.ts`)

## What

`replay(ctx, id)` (core §H.1) is "dead → pending, audited". For a `StoreCtx` the audit row is P5's:

```ts
// src/lib/jobs/outbox.ts (P8)
export async function replay(ctx: StoreCtx | PlatformCtx, id: string): Promise<void> {
  // … state checks, dead → pending (and done → pending for telegram / webhook) …
  if (isPlatformCtx(ctx)) await auditFrom(ctx, "platform.outbox.replayed", { … }); // the console's row, unchanged
  // a StoreCtx: no audit row here. src/lib/integrations/replay.ts writes `integrations.outbox.replayed`
  // { kind, topic, outboxId, resend } once per replayed row (OPE-§Q.26), after this call returns.
}
```

The rules P5 applies before calling `replay` (so P8's need not repeat them for a store, but may as a belt):

- the row is the store's own and a tenant kind (`mail` and another store's id answer the seam's `not_found`);
- `pending` / `running`: a no-op, `replay` is not called;
- `done`: only `telegram` and `webhook` (Send again); `capi` and `mail` refused before `replay`;
- `cancelled`: refused before `replay`;
- the bucket `s:<sid>:replay:<uid>` 30 / h, charged once per call; "Replay all dead" ≤ 50 rows per call.

## Why

- OPE-§28.1 / §M.3: the action audits `integrations.outbox.replayed` with `{ kind, topic, outboxId }`, and
  `test:integrations-db` proves "one audit row per replayed row". If the core also wrote the row for a store, each
  replay would leave two.
- The bucket and the ≤ 50 cap are store-side rules (OPE-§L): they belong next to the store's audit row.

## Meanwhile

`replay` is the P0 stub in this worktree. `src/lib/integrations/replay.ts` calls it through `setReplayDoubleForTests`
(the tests' double moves `dead`/`done` → `pending`). The tenancy cases never reach the stub (the attack ids are
refused first; B's own cases use a pending row and kinds with no dead rows).

## If P8 prefers the core to write the row

Then the maintainer deletes the `auditIn(…, "integrations.outbox.replayed", …)` line in
`src/lib/integrations/replay.ts` `replayed()` at the merge and the core writes the same name and meta; the
`test:integrations-db` checks stay as they are (one row per replayed row).
