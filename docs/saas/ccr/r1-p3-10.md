# r1-p3-10: the render context carries the document's add-ons and the store's shopper facts

- Status: open (filed at P3 wave 1, step p3-w1-shopper-html). Applied by the maintainer at the P3 wave 1 merge. Nothing
  breaks while it is open: the order form and the thank-you read both fields through P3's adapter
  (`src/landing/addons/facts.ts`), which answers "absent", so the delivery slots stay empty and hidden, the thank-you
  slots are not rendered, the address follows the doc's `form.address`, and the timeline keeps the call step and promises
  no inspection. `test:render` proves the filled states by rendering the section and the thank-you body over a context
  that carries the two fields (`scripts/qa/render-cases/landing.ts`).
- Merge note (P3 wave 1 merge, 2026-11-06): applied through the one choke point: `contextFor` copies `addons` and `shopper`; `renderLandingHtml` / `renderThankYouHtml` apply `applyShopperFacts(doc, opts.shopper)`; the store render context reads `checkout` + `policies` and `storeRenderOptions` passes `shopper` (live publish, re-render, test render, preview route); the builder preview passes `rc.shopper`. `RenderContext` keeps the two fields through P3's adapter cast (types.ts unchanged) and exports carry no `shopper` yet: both deferred to the integration.
- Filed by: P3 LANDING · Owners of the files: the maintainer (`src/landing/types.ts`, §K.3) and the render files no R1
  row owns, which the maintainer edits at the merge (`src/lib/render/core.ts`, `src/lib/render/store-context.server.ts`,
  `src/lib/render/test-render.server.ts`, `src/lib/editor/preview.server.ts`, `src/lib/export/bundle.ts`)

  `applyShopperFacts`, `addonBlock`, `shopperOf`)

## What

1. `src/landing/types.ts`, `RenderContext` gains two optional fields (after `links`):

   ```diff
   +  /**
   +   * The add-ons this document embeds (§H.13): sections read their own data block for the server fallback (the
   +   * order form's delivery line, LAN-§7.4; the thank-you blocks, LAN-§8.1). Absent: no add-on.
   +   */
   +  addons?: import("./addons/types").RenderAddons;
   +  /** The store's shopper facts (LAN-§3.5 OF2, §6.3): P3's `ShopperFacts`. Absent: QA renders and exports before this CCR. */
   +  shopper?: import("./addons/facts").ShopperFacts;
   ```

   (P3's adapter type `ShopperRenderContext` then equals `RenderContext`; P3 drops the cast in its next step.)

2. `src/lib/render/core.ts`: `RenderHtmlOptions` gains `shopper?: ShopperFacts`, and `contextFor` copies both fields
   into the context, so the document's add-ons reach the sections that render them:

   ```diff
    function contextFor(doc: PageDoc, opts: RenderHtmlOptions): LandingRenderContext {
   -  return createRenderContext(doc, {
   +  const ctx = createRenderContext(doc, {
        mode: opts.mode,
        …
      });
   +  return { ...ctx, ...(opts.addons ? { addons: opts.addons } : {}), ...(opts.shopper ? { shopper: opts.shopper } : {}) };
    }
   ```

   `renderLandingHtml` and `renderThankYouHtml` already pass `opts.addons` (the landing half, resp. `thanksAddons`), so a
   thank-you context carries the thank-you add-ons. `renderLegalHtml` takes neither (legal pages take no add-on, P0b
   P3-2); its policy answers come through r1-p3-2.

3. `src/lib/render/store-context.server.ts`: the store render context reads `checkout` and `policies` (it already
   reads `checkout` for the endpoints) and carries `shopper: shopperFactsFor(checkout, policies)`; every caller that
   renders a store document (`publish.server.ts`, `test-render.server.ts`, `store-routes.server.ts`,
   `editor/preview.server.ts`, `export/server.ts`, `export/bundle.ts`) passes `shopper: rc.shopper` in the options **and
   renders `applyShopperFacts(doc, rc.shopper)`** instead of `doc`, so the form's address row and the runtime config's
   `fields.address` follow the same mode (`hidden` is not honoured while the store requires it, UX-31).

## Why

- LAN-§7.4: the slots `[data-lp-dz]` hold "the server fallback text (no JS, exports, the builder's interactive
  preview)", the same general line the `assist` chunk composes on load. The text is a function of the `lp-assist` block
  (the zone table, the page's words, the fee), which today reaches only the Shell, never a section.
- LAN-§8.1: the expectation's fallback is "the sentence without `{when}` when a caller phone exists", and the three
  blocks render only when their block is on (LAN-§3.6: with every block off, the thank-you keeps its bytes). Both need
  the `lp-assist-ty` block in the body.
- LAN-§3.5 OF2 (UX-31): the address row follows `checkout.addressMode`; LAN-§6.3: the call step only with
  `checkout.confirmationCall`, "check, then pay" only when `policies.inspection = "allowed"`. Neither setting is in the
  render context today.

## Effect

- A store page with zones on prints "Livraison en 1 à 3 jours ouvrés selon la ville · 35 DH" under the offers before
  any script runs; a store without zones keeps both slots empty and hidden (today's state on every page).
- A thank-you page with its blocks on gains the confirm pill beside the order chip, the expectation in the call step
  and the tracking link in the summary footer; with them off it is unchanged.
- The thank-you timeline follows the store's answers; an export (no `shopper`) keeps the call step and the plain "pay
  on delivery" step.
- Goldens: the store documents of stores with zones or blocks on change as above; QA renders (no `shopper`, no
  add-ons) do not.
