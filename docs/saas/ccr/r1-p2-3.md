## Why

around the P0 read APIs: R1.0's `getDashboard` (with its six-item setup checklist) and `navCounts` give way to
`dashboardPanels` and the pulse (D57), and R1.0's cross-table LIKE `searchAdmin` to `searchStore` over the registered
search providers (ADM-02). The maintainer's harness still names the three old functions in `repositorySuite`, so P2
keeps them as **deprecated shims** today (tsc and `test:tenancy` stay green):

| Old name | Shim body today | Harness lines |

| `getDashboard(scope, store, user, opts)` | `dashboardPanels({ scope, store, can }, "7d")` with no viewer (the per-viewer panels are `hidden`) | `same(fx, "getDashboard(B)", …)`, `masked("getDashboard(A, impersonation)", …)` |
| `navCounts(scope)` | R1.0's two counts, unchanged; no app code calls it any more (the layout paints the pulse's counts) | `same(fx, "navCounts(B)", …)` |

(dashboard panels of B, A's impersonation scope, the review card, preview links, the invite count, `searchStore`, the
pulse and search routes, the rename), so §1 only moves the harness's generic lines onto the new names.

## 1c. Note: staff views count on a platform bucket

The impersonation suite calls every tenant route as staff viewing A and requires A's rows unchanged but for the audit
of refused writes. A store bucket (`s:<A>:pulse:<staffId>`) is one of A's rows in that fingerprint, so P2's pulse and
search routes count a staff view (`ctx.impersonation` or a synthetic membership) on `p:pulse:<userId>` /
`p:search:<userId>` instead; members keep core §E.8's `s:<sid>:pulse:<userId>` and `s:<sid>:search:<userId>`. No
harness change is needed for this; it is recorded so §E.8's table can carry the footnote at the integration.
