# r1.0-t2-1: `checkSameOrigin` / `assertSameOrigin` accept the request headers of a server action

- Status: open
- Filed by: T2 · Owner of the file: T3
- Files: src/lib/security/csrf.ts

## What

§C.9 and §E.2 write `assertSameOrigin(headers())`: the action wrappers (`storeAction`, `userAction`,
`platformAction`) have only the `Headers` of `next/headers`, not a `Request`. Today's csrf.ts takes a `Request`.
Add a headers form next to the existing one, with the method fixed to POST (a server action is always a POST):

```ts
/** The §C.9 check for a state-changing request: a Request, or the headers of a server action (method POST). */
export function checkSameOrigin(req: Request | Headers): boolean;
/** Throws CsrfError (403) unless same-origin. Server actions pass `await headers()`. */
export function assertSameOrigin(req: Request | Headers): void;
```

For a `Headers` argument the safe-method shortcut never applies (treat it as POST). Everything else is the strict
rule T3 implements anyway: `Sec-Fetch-Site: same-origin`, an `Origin` whose host is `PLATFORM_HOST` or
`ADMIN_HOST`, a missing `Origin` refused, `Origin: null` refused, no reflection of `Host` / `X-Forwarded-Host`.

## Why

Until it lands, `src/lib/tenancy/seam.ts` (`assertActionOrigin`) wraps the headers in
`new Request("http://localhost/", { method: "POST", headers })`. That works, because `checkSameOrigin` reads only
headers, but it relies on an internal detail of csrf.ts. The seam also refuses a missing `Origin` itself
(`isSameOriginMutation`) so SEC-11 holds whichever track merges first; with the strict csrf.ts the two rules agree.

## Effect on others

- T2 switches `assertActionOrigin` to `assertSameOrigin(h)` after the merge (one line, its own file).
- No other caller changes: the `Request` form stays.
- `test:security` (T3) gains one case: the headers form refuses a missing Origin and accepts a same-origin action.
