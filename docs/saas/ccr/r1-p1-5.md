## 1. The `src/lib/platform/**` pin (maintainer, `scripts/qa/tenancy-allow.json`)

### Why

P0b P1-8 re-counts the pin "at the P1 merge". The approval queue cannot wait for it: the queue lists every store's
open review rows (PLA-§3.5), and a decision names a row by its id without the store (`approveReviewAction({ reviewId })`),
so both reads cross stores by design (core §E.3 rule 6: "console lists … live only in `src/lib/platform/**`, each query
annotated"). The dangerous-action ledger is the same (rows due across stores, the store-less super_admin promotion),
and the sandbox meter reads the five largest pending stores. Every other read of this step goes through
`platformScope(ctx, storeId)` or the store's own system seam and needs no annotation (`lifecycle-preview.ts`,
`lifecycle-actions.ts`, `plans.ts`, the per-store parts of `queue.ts`).

So `npm run test:tenancy-lint` (the last command of `npm test`) reports one violation on `r1/p1`: **PIN, 11 queries
exempted in `src/lib/platform/**`, pinned at 5**. Rules L1-L13 are 0. Every other suite of `npm test` passes.

## 2. Extra audit meta on a transition (T1, `src/lib/tenancy/lifecycle.ts`)

### Why

PLA-§3.5: approving a review audits `platform.signup.approved { reviewId, score, band }`. `transitionStore` writes that
row (the edge's audit action) with `lifecycleAuditMeta(from, to, opts, note, stepUp)`, which has no room for the
caller's facts; a second audit row from the queue would break "each decision writes exactly one audit row" (PLA-§3.5
acceptance). The same holds for a suspension's notice choice (`suspendNotice`, D32), which `runLifecycleAction` saves
on the store row before the transition, so today no audit row records it.

### What

```diff
 export interface TransitionOpts {
   reason: string;
   note?: string;
   notify?: { showNote: boolean };
   stepUp?: StepUpMethod;
   purgeAt?: Date;
+  /** facts of the caller's decision for the edge's one audit row (never from/to/reason/note/noteShown/stepUp) */
+  auditMeta?: Readonly<Record<string, string | number | boolean | null>>;
 }
@@ export function lifecycleAuditMeta(...)
-  return { from, to, reason: opts.reason, ...(note ? { note, noteShown: opts.notify?.showNote === true } : {}), ...(stepUp ? { stepUp } : {}) };
+  return { ...(opts.auditMeta ?? {}), from, to, reason: opts.reason, ...(note ? { note, noteShown: opts.notify?.showNote === true } : {}), ...(stepUp ? { stepUp } : {}) };
```

(`lifecycleAuditMeta`'s `Pick<TransitionOpts, "reason" | "notify">` gains `"auditMeta"`.) P1 then passes
`auditMeta: { reviewId, score, band }` from `approveRow` (src/lib/platform/queue.ts) and `{ suspendNotice }` from
`runLifecycleAction`; `src/lib/audit.ts`'s `AUDIT_SECRET_KEY_RE` already refuses a secret-looking key.

### Meanwhile

The approval's audit row carries `{ from: "pending", to: "active", reason: "approved", note? }`; the review id, score
and band are on the `signup_reviews` row it decided (`decided_by`, `decided_at`).

## 3. The store's words in the lifecycle preview (P2, `shell.ts` and `StoreBanner`)

### Why

PLA-§8.0: `lifecyclePreview().storeSees` is "rendered from shell.* keys in the store's default locale, with the reason
sentence", and the acceptance (case 11) says it equals what the store's banner renders after the write. The keys are
P2's and not on `r1/p1`. P1's `src/lib/platform/lifecycle-rules.ts` renders them with `storeSeesFor()` (pure,
isomorphic); while a key is missing it uses the English text of PLA-§N.2 for the whole banner (never an English
sentence around a French reason) and sets `storeSees.fallback`, which the sheet shows.

### What

1. P2's catalogs carry, in ar / fr / en: `shell.banner.pending`, `shell.banner.restricted` (`{reason}`),
   `shell.banner.suspended` (`{reason}`), `shell.banner.closed` (`{date}`, `{until}`), `shell.page.closed`,
   `shell.page.deletion` (`{date}`), `shell.page.rejected`, `shell.status_reason.<code>` for every code of
   `src/lib/platform/reasons.ts` (`STORE_STATUS_REASONS`), and `shell.appeal.used` (the refusal `submitAppeal` answers
   when the one appeal was used; `AuthRefusal("invalid", "shell.appeal.used")`).
2. `StoreBanner` renders the state banners with `storeSeesFor({ from: status, status, reason: status_reason,
   closedAt, purgeAfter, suspendNotice, locale, timeZone, notification: null }).banner` (or the same keys with the same
   variables, the dates through `storeDay(date, locale, timeZone)`), so the preview and the banner can never differ.

### Proof

`test:platform` prints a SKIP for the store-locale half until the keys exist and then checks the localized banner;
`test:platform-db -- --case 11` compares the preview with `storeSeesFor` over the row each transition wrote.

## 4. Leases in the lifecycle preview (P4 and T1)

### Why

PLA-§8.0: `affects.agentsWithLease` comes from P4 (`queueCounts` / `opsPulse`), and case 11 proves it equals the leases
`releaseAllLeases` released. `QueueCounts` has no lease count, and `transitionStore` does not call `releaseAllLeases`
yet (its header: "the R1 product hooks of the edge … join `afterCommit` when their owners' functions exist").

### What

- P4: `QueueCounts` gains `agentsWithLease: number` (agents holding a live claim on one of the store's orders); P1
  then reads it there instead of counting `orders.claim_token` / `lease_until` itself (the count P1 makes today,
  `lifecycle-preview.ts` `agentsWithLease`, through the store's platform scope).
- T1 (at the P4 merge): `afterCommit` calls `releaseAllLeases(systemScope(…, storeId))` for → `restricted`,
  `suspended`, `closed` (core §A.5.1); P1's case 11 then checks `released === preview.affects.agentsWithLease`
  instead of printing its note.
