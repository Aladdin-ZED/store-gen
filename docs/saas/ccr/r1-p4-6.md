# r1-p4-6: the shell's `error.<code>` messages for P4's own action codes

- Status: filed (R1 P4 step 5). Apply at the P4 merge.
- Filed by: P4 CALL CENTER · Owner of the files: maintainer (core §K.3, §I.5)
- Files: src/lib/i18n/admin/{en,fr,ar}.ts

## What

Core §H.4: "a part answers its own codes (listed in its spec, each with an `error.<code>` message in ar/fr/en)". The
ops catalog (`test:ops` [catalog]) only allows `ops.` keys in P4's per-track files, so P4 shipped the texts as
`ops.error.<code>` in `src/lib/i18n/admin/{en,fr,ar}/ops.ts`. Add one alias per code to the core files:

```ts
"error.blocked": t("ops.error.blocked"),          // or copy the three strings from the ops files
"error.duplicate": …, "error.locked": …, "error.bad_hold": …, "error.bad_adjust": …,
"error.reason_required": …, "error.already_converted": …, "error.illegal": …,
```

(Or, equivalently: let the shell's error sheet look up `ops.error.<code>` when `error.<code>` is missing.)

## Why

`createManualOrder`, `editOrder`, `convertLeadToOrder`, `setOrderHold` and `blockPhoneAndCancel` answer these codes
(OPE-§11.1-§11.4, §9.5, OD49); without a message the shell renders its generic sheet. The drawer and the new-order
sheet (P4 steps 10 and 11) read the `ops.error.*` keys directly, so nothing is blocked meanwhile.
