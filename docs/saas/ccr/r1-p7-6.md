# r1-p7-6: server provider wiring at the P7 merge (built-in call script, notify kinds, spec signatures)

- Status: open
- Filed by: P7 (step 7) · Owners: maintainer (docs/saas/spec/ai.md), P4 (src/lib/callcenter/script-builtins.ts, read only)
- Files: src/lib/ai/provider/library.ts (P7, at the merge), docs/saas/spec/ai.md (AI-§B.1, AI-§B.3)

## What

1. **`callcenter.script` library rung.** AI-§A.5 and the step brief name P4's built-in script
   (`src/lib/callcenter/script-builtins.ts`, OPE-§7.3) as the library rung. That file is not in the P7 base (P4 merges
   before P7, but after this worktree was cut). Until the merge, `libraryValue("callcenter.script")` answers P7's own
   template (`libraryScript` in `src/lib/ai/provider/library-tasks.ts`: the canonical steps, the address-mode step, the
   configured upsell, six objections; a valid `ScriptDoc`). At the P7 merge the maintainer (or P7 in step 14) replaces the
   one `case "callcenter.script"` line with P4's builder:

   ```ts
   case "callcenter.script":
     return builtinScript(i.locale, { addressMode: i.addressMode, upsell: i.upsell !== null }) as AiTaskOutput<T>;
   ```

   (exact name and options as P4 ships them; the output is a `ScriptDoc` either way, so no caller changes).
2. **Notify kinds.** The router sends `ai.auth_failed` (staff, danger, once per key failure) and
   `ai.director_unavailable` (staff, warn, once per 24 h mark) through `notify()`. `NotificationKind` is still `string`
   in the base, so they are stored as is; their `NotificationKindDef` rows and the `notify.ai.*` texts arrive with step 8
   (P7's own `src/lib/notify/kinds/ai.ts` and i18n file). No shared file changes.
3. **Spec text (AI-§B.1, AI-§B.3).**
   - `anthropic()` is `Promise<Anthropic | null>`: the key resolution reads the sealed platform setting (async).
   - `callClaude(spec, env)`: the client, the call shape and the breaker come in through `env` (the router passes
     `anthropic()` and `platform_ai.callShape`), so the call layer reads no setting and `test:ai` drives it with a real SDK
     client over a scripted `fetch`. `CallSpec` gains `pattern` (the director_deep rule is asserted on it) and `fallbacks`
     (the router's `RoutePlan.fallbacks`).
   - The retention 400 of `director_deep` is detected as "a `bad_request` on the first deep call of the process", never
     by matching the message (AI-§B.10 forbids string matching); the spec's "or" already allows it.

## Why

The P7 router must answer every R1 task today with the rungs that exist in its base, and the spec's signatures need to
say what the code does. Nothing here changes another track's file.
