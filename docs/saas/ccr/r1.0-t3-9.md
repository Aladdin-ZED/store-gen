# r1.0-t3-9: V3 also proves that Cloudflare never caches a store document under the apex URL (ENGC-2)

- Status: open
- Filed by: T3 · Owner of the file: maintainer
- Files: `docs/STORE-SAAS.md` §C.10 step 3, `docs/saas/RESEARCH.md` §5.3 (V3)

## What

Extend V3 with:

> Two store hosts, each requested twice on one path (`curl -sI https://a.<domain>/x`, then `https://b.<domain>/x`):
> every response carries `CDN-Cache-Control: no-store`, `cf-cache-status` is absent, `DYNAMIC` or `BYPASS` (never
> `HIT`), and each body names its own store. Then `curl -sI https://<domain>/x` answers the platform's page.

## Why

`edge/worker.js` sends the subrequest with `cf: { cacheTtl: 0, cacheEverything: false }`, as §C.5 specifies.
Cloudflare documents `cacheTtl` as an option that *forces* caching with that edge TTL, so `0` means "expires at
once" rather than "never stored". The guarantee that a store document is never served from the apex URL's cache
entry therefore rests on two things: `cacheEverything: false`, and the origin's `CDN-Cache-Control: no-store` on
everything it serves `via = edge` (documents, SEO files and, since T3 step 4, the canonical 308s too). A zone Cache
Rule configured later with an Edge TTL override that ignores origin headers would defeat both. `qa:edge-sim` proves
the app side offline and has a negative control, but only a live check on the real zone can prove the zone side.

If V3 ever shows a `HIT`, the fallback is the Workers `cache: "no-store"` fetch option (compatibility date
2024-11-11 or later), which bypasses the cache outright. It is not the default, because with an older compatibility
date the fetch throws.
