## 1. The tenant download route of a store export (PLA-§22.11, core §F.9)

Settings → Danger zone lists the newest export's parts with download links. P8's `exportPartStream(scope, jobId, part)`
exists as a stub, but no tenant route serves it and no R1 row owns one. The page links each part to:

```
GET /api/app/<handle>/store-export/<jobId>/<part>     → src/app/api/app/[store]/store-export/[job]/[part]/route.ts
```

The route must re-check `store.export` on the session and a fresh step-up (core §F.9: "a link copied out of the page is
useless without the second factor"), answer `403 { error: "step_up" }` otherwise (the shell's `isStepUpAnswer`), and
stream `exportPartStream(ctx.scope, job, part)` with `Content-Disposition: attachment`, `Cache-Control: private,
no-store`. Ask: add the folder to P8's row (it owns the stream), or to P2's `src/app/api/app/[store]/**` list, and the
headers-check case. Until then `listExportJobs` is a stub too, so the page shows "Exports aren't available yet" and no
link is rendered.

## 2. The picker's second sort key (PLA-§22.3, TN-07)

`/app` sorts the stores by `sessions.last_store_id` first, then by `store_members.last_active_at`. The picker reads
`switcherData(user)` (T2's `src/lib/auth/landing.ts`, no R1 owner), whose `MembershipSummary` has no `lastActiveAt` and
is ordered by name. P2 cannot read `store_members` across stores itself (a `tenancy: platform` query outside an
allow-listed file). Ask, in `src/lib/auth/landing.ts`:

```ts
export interface MembershipSummary { …; lastActiveAt: string | null }   // store_members.last_active_at, ISO
// listMemberships: select storeMembers.lastActiveAt; keep the name order (the picker sorts)
```

P2 then sorts `(last store first) → lastActiveAt desc → name`. Until then: the last store first, then usable stores,
then the name order.

## 3. `/api/auth/handle?h=` has no R1 owner (PLA-§22.1, §22.10.2; core §C.7)

The rename field's live check (Settings → Address) uses the signup's seam-wrapped `checkHandleAction` (public action,
bucket `p:handle:ip:<hash>`, burst floor) with the 250 ms debounce the spec asks, and shows "Available" / "Not
available" only. The behaviour matches the route the spec names; if the maintainer wants the route itself, it needs an
owner (P2's `(public)` glob does not cover `src/app/api/auth/**`). No change asked otherwise.

## 4. Recorded drift: the audit page's permission (PLA-§22.10.6)

The spec gives Settings → Audit `settings.read`; T1's frozen `listStoreAudit` guards on `audit.read`, so the page asks
`audit.read` (the nav registry already lists the tab under `audit.read`). A member with `settings.read` but without
`audit.read` gets the neutral 404 there. If the spec is meant, the matrix grants `audit.read` with `settings.read`
(maintainer, `src/lib/auth/permissions.ts`); no P2 change follows either way.
