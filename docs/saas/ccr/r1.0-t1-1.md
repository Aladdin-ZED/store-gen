## What

Add the `platform_usage` table of §D.5 to 0004, with `period` widened from `varchar(7)` to `varchar(13)`.

`src/lib/db/schema.ts`, in the tenancy block (after `storeUsage`):

```ts
/** Platform counters (§D.7; D69): "YYYY-MM", "YYYY-MM-DD", the hour "YYYY-MM-DDTHH" or "total". */
export const platformUsage = mysqlTable(
  "platform_usage",
  {
    metric: varchar("metric", { length: 32 }).notNull(),
    /** rev 3 (D69): created wide for the hourly mail counter, never MODIFYed (like store_usage, ENGC-17) */
    period: varchar("period", { length: 13 }).notNull(),
    value: bigint("value", { mode: "number" }).notNull().default(0),
    updatedAt: updatedAt(),
  },
  (t) => [primaryKey({ columns: [t.metric, t.period] })],
);
```

`drizzle/0004_tenancy.sql`, beside the other `CREATE TABLE IF NOT EXISTS` statements (guarded and idempotent like them):

`drizzle/meta/0004_snapshot.json`: the matching table entry (regenerate it with the rest of the snapshot). In §D.3, move
the `platform_usage` row from 0005 to 0004; in §D.5, take the table out of the 0005 block and change the column to
`varchar(13)`.

## Why

R1.0 charges this table, but 0004 does not create it:

- T2's daily sandbox ceiling (D69, §B.2 step 6) opens with `chargePlatformUsage("pending_stores", <day>, 1, { limit })`;
- the media upload route (§G.4 step 4) charges `pending_media_bytes` for pending stores;
- `transitionStore` out of `pending` refunds it (§A.5.1).

`period` is `varchar(7)` in §D.5, which fits only "YYYY-MM". `pending_stores` needs "YYYY-MM-DD" (10 characters), and
`mail_sent` is hourly (§D.7). T1's `platformPeriodOf("hour", at)` writes "YYYY-MM-DDTHH" (13 characters). A later
`MODIFY` is what rev 3 ENGC-17 avoided for `store_usage`. This is the drift the C0a report notes (§7 item 2).

## Meanwhile

`src/lib/tenancy/usage.ts` uses this exact shape. Until the table exists, `chargePlatformUsage`,
`refundPlatformUsage` and `platformUsageValue` throw an error that names this CCR (MySQL errno 1146). No other table
changes. `transitionStore` logs the failed `pending_media_bytes` refund and completes the transition. T1's DB check
creates the table by hand with this DDL; its results are in the T1 step 2 report.

## Effect on others

- T2: `signupAction` can charge the D69 day counter as soon as this is applied.
- P1 (R1 product): the console meters read `platformUsageValue`.
- `test:migrate`: the live schema equals the snapshot, so the snapshot must include the table.
- No frozen contract changes: PageDoc v2, runtime config v2, payload v2, the PHP export and the landing chunk are
  untouched.
