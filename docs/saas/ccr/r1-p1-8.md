## 1. The two public action files are not store actions (maintainer, `scripts/qa/tenancy-check.ts`)

### Why

Step 7 adds P1's two public forms (PLA-§M.1, §P.1): `src/app/(public)/report/[handle]/actions.ts`
(`reportStoreAction`, a `publicAction("report")`) and `src/app/(public)/invite/staff/[token]/actions.ts`
(`acceptStaffInviteAction`, a `publicAction("invite:accept")`). Neither takes a store from a path: the report resolves
its handle inside `recordAbuseReport` (an unknown handle writes nothing), the staff invite has no store at all. The
coverage rule derives every "use server" file outside `NOT_STORE_ACTIONS` as a store action, so `test:tenancy` and
`qa:action-replay` fail `action … has an attack case` for both until they are listed, like T2's own public forms.
Their attack cases are P1's (`scripts/qa/tenancy-cases/platform.ts`, PLA-§O.3 case 17; platform-check case 20).

### What

```diff
 export const NOT_STORE_ACTIONS: Record<string, string> = {
   "src/app/(public)/actions.ts": "the language menu (T2): signed out or in, no store",
   "src/app/(public)/invite/[token]/actions.ts": "invite acceptance (T2): the store comes from the hashed one-time token, never a path (selftest-team)",
+  "src/app/(public)/invite/staff/[token]/actions.ts": "staff invite acceptance (P1): no store; the hashed one-time token binds the e-mail (PLA-§14.1)",
+  "src/app/(public)/report/[handle]/actions.ts": "the public abuse report (P1): no session; the handle is resolved inside recordAbuseReport, an unknown one writes nothing (PLA-§24.2, case 17)",
   "src/app/(public)/login/actions.ts": "sign-in (T2): no store, no session yet",
```

Until then the two coverage checks are the only red lines of `test:tenancy` on `r1/p1` this step adds.

## 3. The settings audit carries the section and the changed paths (maintainer, `src/lib/settings/index.ts`)

### Why

PLA-§13: each console save is audited `platform.settings.updated { key, section, changed: [paths] }`.
`setPlatformSetting` is the one writer and audits `{ key, fields }` itself, so `savePlatformSettings`
(`src/lib/platform/settings-admin.ts`) cannot add the section and the changed leaf paths without a second row.
Meanwhile the console writes through `setPlatformSetting` unchanged (one row, `fields` = the top-level keys) and the
action answers the changed paths to the page.

### What (additive)

```diff
-export async function setPlatformSetting<K extends PlatformSettingKey>(key: K, input: PlatformSettingInput<K>, actor: PlatformActor): Promise<PlatformSettingValue<K>> {
+export async function setPlatformSetting<K extends PlatformSettingKey>(key: K, input: PlatformSettingInput<K>, actor: PlatformActor, audit?: { section?: string; changed?: string[] }): Promise<PlatformSettingValue<K>> {
 …
-    meta: { key, fields: fieldNames(value) },
+    meta: { key, fields: fieldNames(value), ...(audit?.section ? { section: audit.section } : {}), ...(audit?.changed ? { changed: audit.changed.slice(0, 50) } : {}) },
```

P1 then passes `{ section, changed }` from `savePlatformSettings` (one line).

## 5. Spec wording: a tenant session on a console action answers `not_found` (spec sync, PLA-§O.2 case 12)

PLA-§O.2 case 12 says `addImpersonationNoteAction` "from a tenant session → `forbidden`". The platform seam
(`src/lib/platform/seam.ts`, maintainer) answers a session without a platform role with the neutral `not_found`
(PLA-§O.3 case 4 already reads "not_found / forbidden"). The tests accept either code and assert that nothing is
written; the spec line should read "→ refused (`not_found`, the neutral answer)".
