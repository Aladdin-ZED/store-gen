# r1-p3-4: the harnesses that publish the library's pages pass the honesty gate through (or publish an honest page)

- Status: open (filed at P3 wave 1, step p3-w1-gate-checklist-health). Applied by the maintainer at the P3 wave 1
  merge, when the honesty gate (`registerPrePublishCheck("landing", …)`) starts answering for every publish.
- Filed by: P3 LANDING · Owner of the files: the maintainer (`scripts/qa/tenancy-check.ts`, `scripts/qa/e2e/r1.0-exit.ts`, §K.3) and the R1.0 files
  no R1 row owns, which the maintainer edits at the merge (`scripts/qa/migrate-check.ts`,
  `scripts/qa/pixels-publish-check.ts`, `src/lib/render/selftest-public.ts`)
- Files: the five harnesses above; P3's helper `withoutLandingGate` (src/lib/render/prepublish/landing.fixtures.ts)

## What

Until P3 merges, the "landing" check registers nothing, so every publish passes the honesty rows. From the P3 wave 1
merge the gate refuses what LAN-§3.2.1 says it refuses, and the library's fixture pages (`getFixture`, the seeded
`/argan` documents) carry exactly that: visible proof sections still flagged `sample` (`honesty:sample`), library
figures (`honesty:D2`), library numbers with no generation record (`honesty:D1`, every field `library`, so
`generated`), the library's "Vérifiez avant de payer" lines with inspection unset (`honesty:promise`). The harnesses
that publish those pages to prove something else (two-store isolation, files, pixels, migrations) then fail on
`honesty_blocked`, which is the gate working, not the case they test.

Each such publish runs inside P3's test helper, which passes the "landing" check through and registers the gate
again afterwards:

```ts
// src/lib/render/prepublish/landing.fixtures.ts (P3, test code; production never imports it, it throws there)
export async function withoutLandingGate<T>(fn: () => Promise<T>): Promise<T>;
```

## Why

LAN-§3.2.1 and core §M.1 rule 3: the honesty rows are hard in every mode, so no harness can switch them off through
`mode: "warn"`. The library's documents are the generator's raw output, the very thing LD17 and owner rule 4 forbid
publishing before the owner attests it; a harness that is not about honesty should not have to forge attestations,
policies and generation records to publish one. The registry already allows re-registering a check under its name
("a second registration under one name replaces the first"); the helper does that for the duration of `fn` and puts
`landingCheck` back in a `finally`, so a failing case never leaves the gate off.

## Effect

- No production behaviour changes: the helper lives in P3's fixtures file, which only tests import, and throws under
  `NODE_ENV=production`.
- `test:tenancy` in P3's tree proves the helper: the library's page is refused (`honesty_blocked`), published inside
  `withoutLandingGate`, and refused again after it (case "landing: A's attested facts, proof, zones and policies
  never reach B's gate or Store Health").
- The honesty gate's own refusals stay covered where they belong: `test:honesty` (every LAN-§3.2.1 fixture),
  `test:checklist` (panel = gate) and the landing tenancy cases (two stores).
