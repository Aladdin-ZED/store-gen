# r1-p5-11: the outbox honours a handler's `retryAfterMs`, and tells a handler that a claimed row is a re-send

- Status: open (P8 applies it in `src/lib/jobs/outbox.ts` `drainOutbox` / `replay`; P5 codes against today's types)
- Owner of the change: P8 PLATFORM OPS (`src/lib/jobs/outbox.ts`)
- Asked by: P5 INTEGRATIONS, step 7 (`src/lib/jobs/handlers/telegram.ts`)

## What

Two additive, optional fields. No existing caller changes.

```ts
// src/lib/jobs/outbox.ts (P8)
export type SendResult =
  | { ok: true; status?: number }
  | { ok: false; retry: boolean; status?: number; error: string; /** NEW: wait at least this long before the next try */ retryAfterMs?: number };

export interface ClaimedItem<P = unknown> {
  // … unchanged fields …
  /** NEW: the row was delivered before and came back through `replay` (a deliberate re-send, core §H.1, ENGC-29) */
  resend?: boolean;
}
```

1. In `drainOutbox`, where a retryable failure is recorded: `next_at = now + max(OUTBOX_BACKOFF_MS[attempts - 1], retryAfterMs ?? 0)`,
   capped at 24 h. The attempt is counted as today; `isFinalFailure` is unchanged.
2. `replay(ctx, id)` of a `done` row (kinds `telegram`, `webhook`) keeps `done_at` as it is (or the drainer sets
   `ClaimedItem.resend = true` for such a row): either lets the handler know the claim is a re-send.

## Why

- OPE-§21.3: Telegram answers `429` with `parameters.retry_after` (seconds); the item must wait that long (the Bots
  FAQ limits: 1 message per second per chat, 20 per minute per group). Today's backoff ladder starts at 1 minute, so a
  `retry_after` above 60 s would be retried too early and burn the ladder. The handler answers `retryAfterMs` already.
- OPE-§28.1: "a re-sent Telegram `new_order` batch is one message marked (renvoi)". The handler can only mark it when
  it knows the claimed row was delivered before; `ClaimedItem` has no such field.

## Meanwhile

- The handler returns `{ ok: false, retry: true, status: 429, error: "rate_limited", retryAfterMs }` (a
  `TelegramSendResult`, assignable to `SendResult`), and keeps an in-process block per chat until `retry_after` has
  passed: a claim before then returns the same retry without calling Telegram. With today's drainer the item waits
  the ladder's step (1 min, 5 min, …), which honours any `retry_after` up to that step.
- The handler reads the claimed rows' `done_at` through the store's scope (`whereStore(outbox, scope, …)`) and also
  accepts `resend === true` on the item. If P8's `replay` cleared `done_at` and set no flag, a re-sent message would go
  out without "(renvoi)" (nothing else changes).

## Tests

`test:integrations-db` (P5) asserts the handler's `retryAfterMs` for a 429, no call before it, and one "(renvoi)"
message for done rows. P8's drainer test adds: a retry with `retryAfterMs = 120_000` on the first attempt gets
`next_at ≥ now + 120 s`; a replayed `done` telegram row is claimed with `resend: true` (or keeps `done_at`).
