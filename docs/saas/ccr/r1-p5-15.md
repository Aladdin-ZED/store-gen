# r1-p5-15: the pulse broadcast's message shape, for screens that refresh on a count

- Status: open (P2 confirms or adjusts at the P2 / P5 merge; P5 codes against the shape below meanwhile)
- Owner of the change: P2 SHELL (the pulse poller), maintainer (`src/lib/pulse/types.ts`, §K.3)
- Asked by: P5 INTEGRATIONS, step 9 (`src/components/admin/integrations/deliveries-log.tsx`)

## What

OPE-§28.1: the integrations page "polls the pulse's `syncFailed` and refreshes the deliveries list on change (one poller
per browser, core D57)". `src/lib/pulse/types.ts` names the channel, `BroadcastChannel("sg-pulse:<storeId>")`, but not
the message posted on it, and P2's poller is not in P5's base. The deliveries log therefore listens to that channel and
reads the count from either shape:

```ts
const data = e.data as { pulse?: Partial<StorePulse> } & Partial<StorePulse>;
const n = (data?.pulse ?? data)?.counts?.syncFailed; // a number, else the message is ignored
```

The first number seen is the baseline; a later different number refreshes the first page and calls `router.refresh()`.
No request of its own, no timer.

## Ask

1. P2's poller posts every fresh `StorePulse` (a 200, not a 304) on `sg-pulse:<storeId>`, either as the pulse itself or
   as `{ pulse }`; the tab that polls also delivers it to its own listeners (a `BroadcastChannel` does not echo to the
   posting object: the poller dispatches locally too, or every listener opens its own channel object, as P5's does).
2. Add one line to `src/lib/pulse/types.ts` naming the message: `export type PulseMessage = { pulse: StorePulse }` (or
   the bare pulse), so screens type it instead of guessing. If P2 also exports a `usePulse()` hook, P5 switches to it
   at the merge (a two-line change in `deliveries-log.tsx`).

Until then the page shows the server's list at load and after each Replay / Replay all; nothing breaks without the
poller.
