## Why

Core §I.5 / D36 and the p2-02 design decision: the store layout now renders the shell chrome in the viewer's language
and direction (`users.locale` through T2's `viewerLocale`), so an Arabic member gets a right-to-left sidebar, switcher
and top bar from R1. The screens inside keep English, left to right, until they are translated (`ScreenLocale`, see
§2). P2's chrome works around the physical sides of the shadcn primitives in its own files; the primitives themselves
are not P2's.

## 2. Cross-track note: opting a screen into the viewer's language

- `StoreFrame` wraps every screen in `ScreenLocale` with the route's list from `screenLocalesFor()`
  (`src/components/admin/shell/store-nav.ts`). The list holds P2's trilingual routes only; each is switched on by the
  P2 step that ships its translated body (today: `/team`, T2's page).
- Another track opts a screen in by wrapping the screen's root: `<ScreenLocale supported={["en", "fr", "ar"]}>`
  (`src/components/admin/common/screen-locale.tsx`); a nested wrapper overrides the frame's. P4's agent queue
  (trilingual in R1, OPS-17) is the first expected user; the operations screens that ship `fr` with `en` (OD58) pass
  `["en", "fr"]`.
- Inside a translated screen, phones, order ids, URLs, handles and e-mails go in `<Ltr>`
  (`src/components/admin/common/ltr.tsx`, a `<bdi dir="ltr">`).
- The chrome now shows nav labels in the viewer's language: a track whose nav item uses its own message key should
  give that key fr and ar texts, or the item shows its English label inside the Arabic sidebar (the fallback, never
  the raw key).
