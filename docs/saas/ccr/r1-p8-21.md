## What

`src/lib/exports-store` is real from P8 step 8. The three frozen signatures are unchanged. `ExportJobSummary` gained
fields, additively (the contract asserts the function types, which name this very interface).

```ts
const { jobId } = await requestStoreExport(scope, { requestedAs: "member", requestedBy: ctx.user.id }); // < 500 ms
const jobs = await listExportJobs(scope);            // newest first, at most 20
const body = await exportPartStream(scope, jobId, "1");   // P1's console route: null → its neutral 404
```

### `requestStoreExport`

- Any scope of the store works, read-only ones too: a suspended or closed store's member scope (§A.5.3) and P1's
  `platformScope` (D71). The insert runs with a system WriteScope minted in `src/lib/jobs/exports.ts`.
- An active job (`pending` or `running`) answers its own `jobId`. Nothing is inserted and nothing is charged.
- Otherwise the bucket `s:<sid>:export:zip` allows 3 a day. Past it, the call throws `SeamError("rate_limited")`, so
  `storeAction` / `platformAction` answer `{ ok: false, error: "rate_limited" }`.
- `requestedBy` must be a user id (26-char ULID), otherwise a `ZodError` (→ `invalid`).
- It is **not** charged to `exports_month`: a data-portability export is not a PHP export.
- It writes no audit row. The caller writes `store.export_requested` with `meta.stepUp` (P2) or with
  `actor_kind = 'platform'` and the reason (P1), and P1 sends the `store.export_by_platform` notification.

### `ExportJobSummary` (the UX contract, §I.8)

| Field | Meaning |
|---|---|
| `state` | `pending` · `running` · `ready` · `failed` · `expired`: label each one as text |
| `progress` | while `running`: `{ part, entries }` (the part being written, the archive entries so far); else `null` |
| `bytes` | `null` until the job is ready, then the sum of the parts. Never estimate it in the UI |
| `parts[]` | `{ n, name, bytes, href }`. `n` is 1-based (the route's `<part>`), `name` is the download file name `<handle>-export-<YYYY-MM-DD>-<n>.zip`, `href` is a fresh signed link (24 h, never past `expiresAt`) while the job is ready, else `null`. Parts stay listed after expiry, without links |
| `expiresAt` | `doneAt` + 72 h; the files are deleted at the first tick after it |
| `error` | a code: `no_data_dir` (DATA_DIR not set or refused at boot), `no_space` (the estimate exceeds what the last DATA_DIR walk left of the budget), `store_gone`, `cursor_lost`, `part_lost`, `write_failed` (three failed slices in a row) |

Suggested copy keys (P2 owns the strings, ar / fr / en): one per state, one per error code, "Download part n of N",
"Links work 24 hours; files are deleted 72 hours after the export is ready".

### The tenant download

`GET /api/app/<h>/exports/<jobId>/<part>?t=<exp>.<sig>`: `storeGuard(req, h, "store.export")` first, then the
signature `hmac(jobId|part|exp, "export-dl:<storeId>")` in constant time. Every refusal (bad or expired `t`, another
store's job, not ready, expired, a missing part) is the neutral 404 of `guardResponse("not_found", 404)`. The answer
is `application/zip`, `Content-Disposition: attachment; filename="<handle>-export-<date>-<n>.zip"`,
`Cache-Control: private, no-store`, `nosniff`. Every download audits `store.export_downloaded` with `meta.part`.

### P1's console route

`/api/admin/stores/<id>/exports/<jobId>/<part>` (PLA-§7.14) keeps its own staff signature
(`hmac(jobId|part|exp|staffUserId, "export-dl-staff:<storeId>")`) and checks; it then calls
`exportPartStream(platformScope, jobId, part)`. The tenant's `href` in `listExportJobs` is the tenant route: the console
builds its own links. `openExportPart(scope, jobId, part)` (same file) also answers `bytes` and the download `filename`
when the console wants `Content-Length` and the same file name.

### The mail

When the §B.10 mailer is on, a member request sends `export_ready` once, to the requester, linking to
`/app/<h>/settings/danger` (never to a signed URL). A platform request sends no mail from P8.

## Why

PL-09, R1 exit criterion (7). P2 and P1 own the screens; this records the data they read so the screens need no
change at the integration.
