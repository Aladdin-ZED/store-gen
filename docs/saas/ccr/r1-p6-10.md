# r1-p6-10: the design flags read through P1's `flagValue` at the P6 merge

- Status: open (apply at the P6 merge; P1 merges first)
- Filed by: P6 · Owner of the file: P6 (`src/lib/design/flags.server.ts`); the resolver is P1's `src/lib/platform/flags.ts`

- Relates to: DES-§2.9, DES-§7.4 (the kill switch), core §D.4 (`flagValue(key, ctx)`)

DES-§7.4 reads the novelty kill switch as `flagValue('design_novelty_check', ctx) ?? platform_design.novelty`. In P6's
tree `src/lib/platform/flags.ts` does not exist yet (P1 writes it; no P0 stub types it), so P6 cannot import it without
breaking `tsc`. Until the merge, `designFlag(key, scope)` reads the two layers the design check needs itself: the
store's own `flag_overrides` row (scope `store`, not expired), then `flags.default_value`, then the declared default of
`src/lib/flags/defs/design.ts`. Plan, market and rollout rules arrive with `flagValue`.

Decision recorded with it: the effective novelty mode is the **weaker** of the flag and `platform_design.novelty`
(off < warn < on). The flag is seeded with its declared default `"on"`, so a literal `flagValue ?? setting` would make the
console's `platform_design.novelty = "off"` unreachable; with the weaker of the two, either switch turns the check off.
