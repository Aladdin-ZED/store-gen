# r1.0-t2-8: legacy /admin callers of `requireUser()` without a permission

- Status: applied in 958f5db as the interim gate (`searchAction` answers `[]` without `hasAdminAccess()`, before
  `requireUser()`); forwarded to T4 for the conversion to `legacyStoreCtx` (r1.0/t4 already has it): at the T4 merge
  T4's body replaces the interim lines.
- Filed by: T2 · Owner of the files: T4
- Files: src/app/admin/(panel)/actions.ts (and any legacy caller T4 still has when T2 merges)

## What

§E.2 makes `requireUser()` the account guard: a signed-in session, **no admin gate** (tenants never hold it, §B.7).
T2 keeps today's behaviour for every legacy call it can recognise: with the legacy `permission` option, or on a request
that carries a valid gate cookie, `requireUser` still checks the gate and the legacy role exactly as before. The one
case it cannot tell apart is a legacy **server action** that calls `requireUser()` with no permission and is invoked by
its id from a non-admin page (actions are reachable by id from any route).

One such caller reads store data: `searchAction` in `src/app/admin/(panel)/actions.ts` (cross-store `searchAdmin` with
the legacy role). Until T4 converts it to the store seam, please make it gate itself:

```ts
const user = await requireUser({ throwOnFail: true, permission: "pages.read" }); // keeps the gate
// or: await assertAdminAccess(); before the requireUser() call
```

The other legacy no-permission callers act on the caller's own account only (`changePasswordAction`,
`revokeSessionAction`, `revokeOtherSessionsAction`, the 2FA page) and are safe without the gate.

## Why

Between the T2 and T4 merges a signed-in tenant without the gate could otherwise post that action id and read another
store's pages and orders.

## Effect on others

None after T4's conversion (the legacy actions are deleted at the R1.0 integration).
