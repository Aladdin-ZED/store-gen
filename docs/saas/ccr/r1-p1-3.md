## 1. The report IP bucket is counted twice (maintainer, `src/lib/auth/attempts.ts`)

### Why

Core §B.1 / §E.8 and PLA-§24.2 give "Report this store" two buckets: `p:report:ip:<h>` 5 per hour and
`p:report:store:<h>` 20 per day. P1's step brief puts both inside `recordAbuseReport` (`src/lib/platform/abuse-report.ts`),
so every caller (the public action, the DB harness `test:platform-db` case 15) gets the core limits from one place:
`platformBucket("report:ip", hashIp(ip))` and `platformBucket("report:store", handle)`, counted before the handle is
looked up (no oracle).

`PUBLIC_FORM_LIMITS` (`src/lib/auth/attempts.ts:86`) also has a `report` row, so `publicAction("report", …)` counts
the same bucket name, `publicFormBucket("report", ip)` = `p:report:ip:<hashIp(ip)>`, before `fn` runs. With both, one
report adds 2 to the bucket and the reporter is refused at the 3rd report of the hour instead of the 6th (PLA-§24.2
acceptance: "the 6th report from one IP in an hour answers `rate_limited`").

### What

```diff
 export const PUBLIC_FORM_LIMITS: Readonly<Record<string, { limit: number; windowSec: number }>> = {
   signup: { limit: 5, windowSec: HOUR },
   "invite:accept": { limit: 10, windowSec: 15 * 60 },
   reset: { limit: 10, windowSec: 15 * 60 },
-  report: { limit: 5, windowSec: HOUR },
 };
```

and in the header of `src/lib/auth/public-action.ts`, step 3: "(signup 5/h, invite:accept 10/15 min, reset 10/15 min;
the report buckets are `recordAbuseReport`'s, PLA-§24.2)". The in-memory burst floor `BURST_LIMITS.report` (20 per
10 min) stays: it runs before any DB work and is a different budget.

### Meanwhile

P1's `reportStoreAction` (step 7) calls `publicAction("report-store", …, { burst: "report", turnstile: "when-configured" })`:
the name has no `PUBLIC_FORM_LIMITS` row, so only `recordAbuseReport` counts the DB buckets, before and after this
change. Once the row is gone the action may use the plain name `report`; nothing else depends on the name.

### Proof

`npm run test:platform-db -- --case 15`: 6 reports from one IP → 5 rows and `rate_limited`; the 21st report on one
store in a day → `rate_limited` with 20 rows (green on `r1/p1` today, since the harness calls `recordAbuseReport`
directly). Step 7's attack case 17 adds the same counts through `reportStoreAction`.

## 2. `member.joined` lives in P1's `notify.ts` (P2, `team.ts`: keep it out)

PLA-§18.2 lists `member.joined` (`{ member, role }`, P1's spelling of `{ name, role }`: `name` is a refused vars key)
among the kinds of `src/lib/notify/kinds/platform.ts`. P0b moved the texts of the team kinds T2 already sent
(`invite.accepted`, `member.role_changed`, `member.suspended`) to P2's `team.ts` (CCR P2-15); `member.joined` had no
text anywhere, and core §I.5 (D67) says P1's `notify.ts` carries the kinds of `kinds/platform.ts`. So
`notify.member.joined.title` / `.body` are now in `src/lib/i18n/admin/{en,fr,ar}/notify.ts`. P2 should not add them to
`team.ts` (the coverage test fails on a key in two tracks' files). If the maintainer prefers every team kind in
`team.ts`, the merge moves the two keys there unchanged; `test:platform` checks the merged catalogs, so it stays green
either way.

## 4. `test:tenancy`'s group-filter check assumes no kind is registered (maintainer, `scripts/qa/tenancy-check.ts`)

### Why

P0 review G2's `notificationCases` (special cases) seeds store A's owner three rows (`health.issue_new`,
`ops.new_orders`, `user.password_reset`) and checks that `group: "store"` returns all three, under the title "kinds no
track registered yet read as group 'store'". P1 now registers the PLA-§18.2 kinds: `health.issue_new` is group
`store`, but `user.password_reset` is group `security` (PLA-§18.2 table), so the filter rightly returns two rows and
the check fails on `r1/p1` (`npm run test:tenancy -- --db cod_test_p1_tenancy`: 6,569 passed, this 1 failed). The
same check breaks again when P4 registers `ops.new_orders` in its own group. Every other notification check passes
against P1's reads.

### What

Derive the expectation from the registry instead of a count:

```diff
   const stores = await seen(ownerA, { group: "store" });
   const orders = await seen(ownerA, { group: "orders" });
-  check("notifications: kinds no track registered yet read as group 'store'", stores.length === 3 && stores.every((i) => i.group === "store") && orders.length === 0, { store: idsOf(stores), orders: idsOf(orders) });
+  // the owner's three rows, each in its kind's registered group (an unregistered kind reads as "store")
+  const { notificationKind } = load<typeof import("@/lib/notify/registry")>("@/lib/notify/registry");
+  const ownerRows: [number, string][] = [[ids.aStore, "health.issue_new"], [ids.aOwners, "ops.new_orders"], [ids.aOwnerPlatform, "user.password_reset"]];
+  const inGroup = (g: string) => ownerRows.filter(([, kind]) => (notificationKind(kind)?.group ?? "store") === g).map(([id]) => id);
+  check(
+    "notifications: the group filter follows the kind registry, an unregistered kind reads as 'store'",
+    sameIds(stores, ...inGroup("store")) && sameIds(orders, ...inGroup("orders")) && stores.every((i) => i.group === "store"),
+    { store: idsOf(stores), orders: idsOf(orders) },
+  );
```

### Proof

`npm run test:tenancy -- --db cod_test_p1_tenancy` on `r1/p1`: today 6,569 passed and this 1 failed (measured); with
the diff the check expects `store` = the `health.issue_new` and `ops.new_orders` rows and `orders` = none, which is
what the failing run printed (`{"store":[7,8],"orders":[]}`), so 6,570 should pass (not run: the file is not P1's).
`npm test` does not run `test:tenancy`, so it is green either way.
