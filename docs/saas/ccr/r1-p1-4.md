## 1. `getHealth` for the `platform.alarms` job (P8 + maintainer)

### Why

PLA-§15.2: the job "evaluates `getHealth()`'s cheap subset". The frozen signature is `getHealth(ctx: PlatformCtx)`, and a
cron job has a `SystemCtx` only (core §E.2): there is no staff member to put in a `PlatformCtx`, and minting one for the
job would give it a staff identity and every `can()`. So on `r1/p1` the machinery source of `src/lib/platform/alarms.ts`
(`DEFAULT_ALARM_SOURCES.machine`) answers `null` and the alarms it feeds (`no_tick`, `outbox_dead`, `db_*`, `data_dir_*`,
`inodes_high`, `error_spike`, `sheets_backlog`, `commerce_quiet`, `render_*`, `edge_*`, `pool_wait`, `tick_lag`,
`design_tables_large`) stay silent, never guessed. Their rules are written and tested on fixtures (`alarmsFrom`,
`test:platform` section 15).

### What

Either of:

```diff
-export async function getHealth(ctx: PlatformCtx): Promise<PlatformHealth> {
+export async function getHealth(ctx: PlatformCtx | SystemCtx): Promise<PlatformHealth> {
```

(and the matching line of `src/lib/contracts/r1-p0.ts`), or a second export for the job:

```ts
/** The fields the alarms read (cron, outbox, storage, dataDir, errors24h, renders, edge, db, tick, commerce, sheets, design), no per-store lists. */
export function healthForAlarms(ctx: SystemCtx): Promise<PlatformHealth>;
```

Then the P1 merge sets `machine: (now) => getHealth(systemCtx("platform.alarms"))` (or `healthForAlarms`) in
`DEFAULT_ALARM_SOURCES`; nothing else changes.

### Three fields the frozen shape lacks (P8, additive)

- `build.sha`: the build's own commit (`qa/.build-sha`, CCR P8-11). `gate_mismatch` compares it with `build.gateSha`;
  without it the alarm stays silent.
- `errors1h: { area; code; count }[]` (or the hour's count beside each `errors24h` row): `error_spike` is "> 50 of one
  code in an hour"; from the 24 h rows P1 counts a code only when its first and last occurrence are under an hour apart.
- `edge.badKeyMaxPerMinute24h`: `edge_bad_key` is "≥ 10 in a minute"; P1 reads `badKey24h ≥ 10` meanwhile (the
  sentence says "in 24 h").

## 2. "Recompute now" counts its bucket once (P2)

`requestHealthRecompute(ctx)` (P1, PLA-§6.3.4) counts `s:<sid>:health:recompute` 6 per hour itself and throws
`SeamError("rate_limited")` past it, so every caller gets the core limit. P2's `recomputeHealthAction` must not pass
`rate: { name: "health:recompute", … }` to `storeAction` as well (the bucket would count twice and refuse the 4th press).
`snoozeHealthIssue` / `unsnoozeHealthIssue` throw `SeamError("forbidden")` without `health.snooze`,
`SeamError("impersonation_read_only")` under impersonation and `SeamError("not_found")` for an issue the row does not
hold; `storeAction` answers them as is. PLA-§O.3 case 9 (step 7) proves the three through the actions.

## 5. Which statement is the `src/lib/health/**` exemption (maintainer)

Core §E.3 rule 6 and PLA-§6.3.4 say the one cross-store statement of `src/lib/health/**` is "the `store_health`
upsert". On `r1/p1` the upsert needs no exemption: it takes the store's `WriteScope` (`systemScope`) with
`storeValues` / `whereStore` under a row lock (`src/lib/health/rows.ts` `commitSnapshot`), so lint L1-L6 pass on it.
The one annotated statement is the queue view `scanHealthRows` (dirty rows by `dirty_at`, stores without a snapshot,
the oldest `computed_at`, `sh_due_idx`; the alarms read their stale and flagged rows through the same SQL text). The
pin stays 1; the wording of rule 6 and PLA-§6.3.4 should name the queue view instead of the upsert.

`breakglass_unreviewed` (PLA-§14.3, §15.2) needs one more cross-store `audit_log` read in `src/lib/platform/**`, whose
pin is 5 and full on `r1/p1` (the view-as rows and the store-less notification rows), so `npm test`'s lint would fail
before the P1 merge re-counts it (P0b P1-8). Until then `DEFAULT_ALARM_SOURCES.breakglass` answers `null` (the alarm
stays silent; its rule is tested in `alarmsFrom`). At the P1 merge: raise the `src/lib/platform/**` pin by one (with
the P1 report's count) and set `breakglass: breakglassSource` with this body in `src/lib/platform/alarms.ts` (the job
reads it at most once an hour, kept in its state row):

```ts
/** The break-glass actions of PLA-§14.3 (with the impersonation, purge and staff-made export prefixes below). */
const BREAKGLASS_ACTIONS = ["platform.pii.revealed", "platform.kill.changed", "platform.backup.downloaded", "platform.user.2fa_reset", "platform.user.reset_link", "platform.order.lookup", "platform.staff.changed"];

/** The ISO weeks older than 14 days with a break-glass row and no `platform.breakglass.reviewed { week }` (the last 10 weeks). */
async function breakglassSource(now: Date): Promise<AlarmInputs["breakglass"]> {
  const from = new Date(now.getTime() - 70 * 86_400_000);
  const reviewFrom = new Date(now.getTime() - 84 * 86_400_000);
  const olderThan = new Date(now.getTime() - ALARM_RULES.breakglassAfterDays * 86_400_000);
  // tenancy: platform the break-glass review state across stores (PLA-§14.3: weeks with a sensitive staff action and no review; codes and weeks only)
  const [rows] = (await db.execute(sql`
    SELECT DATE_FORMAT(created_at, '%x-W%v') AS wk, MAX(action = 'platform.breakglass.reviewed') AS is_review, MAX(JSON_UNQUOTE(JSON_EXTRACT(meta, '$.week'))) AS reviewed
    FROM audit_log
    WHERE created_at >= ${reviewFrom} AND created_at < ${now}
      AND (action = 'platform.breakglass.reviewed'
        OR (created_at >= ${from} AND created_at < ${olderThan} AND (action IN (${sql.join(BREAKGLASS_ACTIONS.map((a) => sql`${a}`), sql`, `)})
          OR action LIKE 'platform.impersonation.%' OR action LIKE 'platform.store.purge\\_%' OR (action LIKE 'store.export\\_%' AND actor_kind = 'platform'))))
    GROUP BY wk, action = 'platform.breakglass.reviewed'
  `)) as unknown as [RowDataPacket[]];
  const reviewed = new Set(rows.filter((r) => Number(r.is_review) === 1 && typeof r.reviewed === "string").map((r) => String(r.reviewed)));
  const weeks = [...new Set(rows.filter((r) => Number(r.is_review) !== 1).map((r) => String(r.wk)))].filter((w) => !reviewed.has(w)).sort();
  return { unreviewedWeeks: weeks };
}
```

(step 12's "Mark this week reviewed" writes `{ week: "YYYY-Www" }`, the format of MariaDB's `%x-W%v` and of
`isoWeek()`).
