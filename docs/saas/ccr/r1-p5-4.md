# r1-p5-4: `syncFailed` has one producer: P5's pulse contributor, over `syncFailedCount`

- Status: open (a note: no change to a frozen file; P4 confirms when it fills `opsPulse`)
- Filed by: P5 · Owner: P4 (`src/lib/orders/queue.ts` `opsPulse`, `src/lib/pulse/contributors/ops.ts`)
- Files P5 wrote: `src/lib/integrations/health.ts` (`syncFailedCount`), `src/lib/pulse/contributors/integrations.ts` (P5)

## What

OPE-§27.3 says both operations contributors call P4's `opsPulse(scope, viewer)`, and `OpsPulse.syncFailed` is
documented as "P5's contributor reports it". Until P4 merges, `opsPulse` is the P0 stub that throws. A contributor
that called it would leave out `syncFailed` on every poll (a failed source omits its key, P0 build note 14) and the
integrations page would never refresh its deliveries list.

So P5 computes the key itself:

| Function | Answers | Reads |
|---|---|---|
| `syncFailedCount(scope): Promise<number>` | failed sheet rows (`sheet_status = 'failed'`, `is_test = 0`) + dead outbox items of the kinds tenants see (`capi`, `telegram`, `webhook`, `carrier`, `whatsapp`; never `mail`) | `orders` (`orders_store_sheet_idx`), `outbox` (`ob_store_idx`), both through `whereStore` |

`contributors/integrations.ts` answers `{ syncFailed }` to viewers who can open the integrations page
(`integrations.manage` or `callcenter.configure`; never an agent, OD12), cached 5 s per store, within 50 ms; a slower or
failed read omits the key.

## Asks to P4

1. `contributors/ops.ts` emits `newOrders`, `dueCallbacks` and `queueNow` only, never `syncFailed`: one key, one
   producer, so the two contributors never disagree on a poll.
2. When `opsPulse` needs `syncFailed` (its `OpsPulse` shape has it), it imports `syncFailedCount` from
   `src/lib/integrations/health.ts` instead of counting the same rows a second way.
