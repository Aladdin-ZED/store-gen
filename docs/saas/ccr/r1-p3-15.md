# r1-p3-15: Campaign Kit (LP-18 = SF-01): `test:kit` in the aggregates, the share-expiry job, the kit input's optional fields

- Status: open (filed at P3 wave 2, step p3-w2-campaign-kit). For the P3 wave 2 merge. Nothing in this step waits on
  it: the kit, its screens, the share page and the suites work today; `test:kit` runs on its own until item 1 lands,
  and shares of ended kits stay valid until a member revokes them until item 2 lands.
- Filed by: P3 LANDING · Owners of the files: maintainer (`package.json`, `src/lib/jobs/slots.ts`,
  `src/lib/jobs/selftest-runner.ts`), contract note only for item 3 (`src/lib/contracts/r1-p0.ts` is untouched).

## What

1. **`test:kit` in the aggregates (LAN-§13.6 "in `npm test`", LAN-§25).** `scripts/qa/kit-check.ts` has an offline half
   (the 60 eval fixtures on the template path, the fingerprint, the `/go` query parity; ≈ 2 s, no database) and a DB
   half (the two-store harness: Go live and the gauge, 410 when paused, 404 after revocation, "page changed since"
   after a republish, the ended kit's refund; a throwaway `cod_test_p3_kit`).

   ```diff
   - "test": "… && npm run test:landing-addons && npm run test:policies && …",
   + "test": "… && npm run test:landing-addons && npm run test:kit -- --offline && npm run test:policies && …",
   ```
   and `npm run test:kit` (both halves) appended to `test:db` beside `test:links`.

2. **`campaigns.share_expiry` (core §H.11, LAN-§13.5: "tokens are revoked automatically when a campaign ends + 90
   days").** A nightly job of slot 6: for each active or restricted store, `UPDATE campaigns SET share_token_hash = NULL
   WHERE store_id = ? AND status = 'ended' AND ends_at < NOW() - INTERVAL 90 DAY AND share_token_hash IS NOT NULL`
   (`whereStore`, one statement per store, audit `campaign.share_revoked` with `meta.reason = "expired"`). The body goes
   in P3's `src/lib/jobs/tracks/landing.ts` once the slot lists the name:

   ```diff
   // src/lib/jobs/slots.ts
   +  "campaigns.share_expiry": "6",
   // src/lib/jobs/selftest-runner.ts (the slot table)
   +      ["campaigns.share_expiry", "6"],
   ```

3. **Contract note: `CompileKitInput` gains optional fields only.** `scripts?` (the store's call script per language),
   `window?` (the calling window: the script's hours line through `weekHoursText`, omitted when `noShopperHours`, as
   LAN-§13.3 asks; the P0 shape had no field for it), `now?` and `leadDays?` (`checkout.confirmationLeadDays`, as the
   page's own ETA). The frozen assertion of `src/lib/contracts/r1-p0.ts` (`compileKit`'s signature and
   `CompileKitResult`) holds unchanged; a caller of the P0 shape still compiles. Recorded so LAN-§13.3's code block can
   show them at the next spec revision.

4. **`test:tenancy`'s `[id]` fixture for `/app/<h>/campaigns/[id]` (`scripts/qa/tenancy-check.ts` `idFor`).** The pages
   suite renders every `[id]` route with A's live page id. The campaign screen therefore also answers a live page's id
   (it opens the create sheet on that page, which the row menu's "Make a campaign" could use too), so the suite is green
   today; the kit screen itself is only rendered by the harness once a campaign fixture exists:

   ```diff
   // fixtures: one draft campaign per store (a direct row, its kit from `compileKit` over the store's live version)
   +  campaign: string;
   // idFor
   +  if (parent === "campaigns") return store.campaign;
   ```

## Why

LAN-§13.6 puts `test:kit` in `npm test`; its DB half cannot run there (no database in `npm test`). The 90-day expiry is
a retention rule of the core (§H.11) that only a registered job can keep. Item 3 keeps the spec and the code saying the
same thing.

## Effect

`npm test` grows by ≈ 2 s; `test:db` by one harness run (≈ 40 s). The job is a no-op on a store with no ended shared kit.
