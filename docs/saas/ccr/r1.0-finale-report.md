The cause is 0004's S1 condition. It counted any `audit_log` row that is not `auth.*` as single-tenant data, and the
old boot's pixel library migration writes two such rows, without a user, even on an install nobody used. In
production the result would have been an active `store-1` / "Store 1" on the `internal` plan with no member. It would
sit beside the store the owner creates at setup, and the tenancy check would report it at every boot. The §D.8 spec's
S1 (`users + pages + orders + assets > 0`) would not have fired. T1 widened the condition at build time to cover every
backfilled table, and the audit clause came with that change.

**Fix (before 0004 ever runs in production):**

1. `drizzle/0004_tenancy.sql` S1: an audit row counts only when it has a `user_id`. The audit backfill (step 4) is

   0004 is safe: drizzle's migrator runs a file only when its `folderMillis` is newer than the last recorded one and
   never re-reads applied files. A database that already ran the old 0004 keeps its result. The owner's local dev
   databases were not inspected.
2. `src/lib/tenancy/convert.server.ts`, the empty-install branch: deletes that one row (`pixel_library`, unencrypted,
   `pixels` an empty array) before writing the marker. Without this the gate would have flagged "1 legacy
   store-level row(s) still in settings". Any other store-level key on an install without store #1 stays where it is,
   and the gate reports it. The boot line names the deletion (`src/lib/db/boot-tasks.ts`).
3. `src/lib/db/upgrade-check.ts`, the pre-tenancy dry run: uses the same audit rule. On an empty install it names the
   empty library row the conversion removes, and it reports every other store-level key as a problem ("nothing would
   own it").
