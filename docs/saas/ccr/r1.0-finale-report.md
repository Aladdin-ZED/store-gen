1. **`test:slow` named three R1 product sweeps that do not exist in R1.0.** C0a declared `test:slow` with
   `test:design:full` (P6's `scripts/qa/design-check.ts`), `test:ai:slow` (P7's `src/lib/ai/selftest.ts`) and
   `test:ai-eval -- --offline` (P7's `scripts/qa/ai-eval.ts`) before any of those files existed, so the gate could not

   file (`test:jobs` and `test:prepublish` are declared in `package.json` and chained nowhere yet). `test:slow` is
   now `npm run theme:check -- --full`, the one slow sweep that exists. The three script names stay as C0a declared
   them; P6 and P7 add them to `test:slow` when they merge. No existing check is skipped: the three never ran.
   Recorded in core §P.5.
2. **The build compiled the boot code into the Edge instrumentation bundle.** `src/instrumentation.ts` opened with
   `if (process.env.NEXT_RUNTIME !== "nodejs") return;`. Turbopack does not drop code after an early `return`, so it
   traced every dynamic import of the boot (`db/migrate`, `db/boot-tasks`, `auth/*`, `security/*`, `edge/host`,
   `jobs/scope`) into the Edge build. It then printed 13 "Node.js API is not supported in the Edge Runtime" warnings,
   each with an "Ecmascript file had an error" line. The same lines show in `next dev`, and the c0a smoke had to keep
   its server log in a file because of them. They would also have appeared in the Hostinger build log, where they look
   like failures. The body is now inside `if (process.env.NEXT_RUNTIME === "nodejs") { … }`, the form Next documents
   (`node_modules/next/dist/docs/01-app/02-guides/instrumentation.md`). The bundler folds that test and drops the
   imports, and the steps 5 and 6 helper moved into the block as well. Node behaviour is unchanged: same order, the
   same `__codBooted` guard, the same early exits. The build now shows 0 warnings, and `qa:r1-exit` checks that a
   production boot applies the migrations to an empty database.
3. **Left as is: one eslint warning**, `_productName` unused in `orderUnits(items, _productName?)`
   (`src/lib/orders/text.ts:120`). The parameter is the documented signature of docs/OFFERS.md §G.3
   (`orderUnits(items, productName)`). Per that contract, v1 rows rebuild with label `""`, so the parameter is
   intentionally unused, and the `_` prefix says so. Removing it means changing the offers contract, and allowing `_`
   arguments means changing an eslint rule. Neither is worth doing for a warning, which does not fail `npm run lint`.
   Not a defect.
