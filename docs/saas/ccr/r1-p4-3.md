# r1-p4-3: `create.ts` keeps honeypot orders out of the risk history, and its `created` event comment

- Status: filed (R1 P4 step 2, p4-transition-events-customers). Item 1 is a fix; apply at the P4 merge or before.
- Filed by: P4 CALL CENTER · Owner of the file: maintainer (core §K.3, D72; OPE-§P read-only list)
- Files: src/lib/orders/create.ts

## 1. Honeypot orders out of the phone's risk history (fix)

Since step 2 the `ops.created` hook moves every honeypot order to confirm `fake` (OPE-§10.2: "the creation hook moves
them to `fake` with reason `honeypot`"), so its projection `status` becomes `fake`. `placeOrder` step 8 counts the
phone's `fake / returned / cancelled / delivered` orders by `status` with only `is_test = 0`:

```ts
// src/lib/orders/create.ts, placeOrder step 8 (today)
.where(whereStore(orders, scope, eq(orders.phone, o.phone.e164), inArray(orders.status, ["fake", "returned", "cancelled", "delivered"]), real))
```

A bot that fills the hidden field with a real customer's phone would then add `history_bad` points (15 to 45) to that
customer's next genuine order. The score never blocks an order (risk.ts), but "This number had 3 orders that did not
arrive" would be a false sentence on the agent's card. The duplicate guard and the per-phone limit of the same
function already exclude honeypot rows (`notHoneypot`); the history should too:

```diff
-      .where(whereStore(orders, scope, eq(orders.phone, o.phone.e164), inArray(orders.status, ["fake", "returned", "cancelled", "delivered"]), real))
+      .where(whereStore(orders, scope, eq(orders.phone, o.phone.e164), inArray(orders.status, ["fake", "returned", "cancelled", "delivered"]), real, notHoneypot))
```

P4's own counters are already safe: a honeypot order never gets a `customers` row (`customer_id` stays NULL), so the
customer history the queue card reads (`ops.history.line`, `customerHistoryOf`) never counts it.

## 2. The `created` event (comment only)

`createOrderRow`'s comment says "With 0005 … the same transaction gains the `order_events` "created" row and the
`INSERT IGNORE` outbox items" (and core D72 lists `order_events "created"` among its parts), but the body writes no
event. P4's `ops.created` hook (afterCommit) writes it, exactly once (it looks for an existing `created` event of the
order first), in one transaction with `city_key`, `priority` and the customer upsert (OPE-§9.1). Two ways to settle it:

- (preferred, no behaviour change) reword the comment: "the `order_events` "created" row is written by the
  `ops.created` hook (src/lib/orders/hooks/ops.ts), once, after the commit; the outbox items by P5's inTx hooks";
- or move the event into `createOrderRow`'s transaction; P4 then drops its write (the hook's existence check already
  makes the change safe in either order).

## Effect on others

- Item 1: the score of an order whose phone a bot used drops back to what R1.0 gave it. No test fixture of
  `test:orders` uses a honeypot row with a real phone's history; `test:tenancy` is unaffected.
- Item 2: none.
